Architecture Deep Dive Android 12L+ / AAOS 관심사 분리(SoC)

Activity Embedding 도입 배경

AAOS 등 대화면 환경에서는 메인 차량 설정 앱이 여러 서비스(음성 인식 등)의 설정 화면 진입점 역할을 합니다. 기존 단일 액티비티 구조는 패키지 간 결합과 배포 병목을 유발하므로, 이를 관심사 분리(SoC) 관점에서 독립된 Activity로 분리 임베딩하여 해결합니다.

As-Is: 단일 Activity 통합 (강결합) 1개 Activity
SettingsActivity VehicleSettings.apk
ListComposable 카테고리 목록
VoiceDetailComposable 음성 설정 UI (종속)
외부 VoiceService.apk와 ContentProvider 결합 · 음성 기능 수정 시 설정 앱도 재배포
To-Be: 2개 Activity 분할 임베딩 (SoC 분리) 2개 Activity
Activity 1 ListActivity 카테고리 목록 VehicleSettings.apk
Activity 2 VoiceDetailActivity 음성 설정 UI VoiceService.apk
각 APK가 자체 Activity 소유 · 외부 ContentProvider 불필요 및 독립 배포 가능
💡 Activity Embedding은 결국 화면 쪼개기(Split)입니다.
두 Activity를 어떻게 쪼갤지 선언하는 SplitRule 등록부터 기술적 내부 원리를 살펴보겠습니다.
1단계: 준비 Zero IPC 인메모리 캐싱

SplitRule 등록

// 1. 대상 액티비티 쌍 매칭 필터 정의 (Primary ➔ Secondary)
val filterSet = setOf(
    SplitPairFilter(
        ComponentName(context, ListActivity::class.java),   // Primary Activity (좌측 분할 창)
        ComponentName(context, DetailActivity::class.java), // Secondary Activity (우측 분할 창)
        null // Intent Action 필터 (null = 모든 액션 허용)
    )
)

// 2. 분할 규칙 정의
val splitPairRule = SplitPairRule.Builder(filterSet)
    .setMinWidthDp(600) // 너비 기준 (600dp 이상 시 분할)
    .setDefaultSplitAttributes(
        SplitAttributes.Builder()
            .setSplitType(SplitAttributes.SplitType.ratio(0.4f)) // 분할 비율 (Primary 40%)
            .setLayoutDirection(SplitAttributes.LayoutDirection.LEFT_TO_RIGHT)
            .build()
    )
    .setFinishPrimaryWithSecondary(SplitRule.FinishBehavior.NEVER) // 우측(상세)이 닫혀도 좌측(목록)은 종료되지 않고 유지
    .build()

// 3. 중앙 RuleController에 등록 (Zero IPC 인메모리 캐싱)
RuleController.getInstance(context).setRules(setOf(splitPairRule))
⚡ 시스템 서버 무통신 (Zero IPC 인메모리 캐싱):
setRules() 호출 시 시스템 서버(ATMS)와의 IPC 통신이 발생하지 않습니다. EmbeddingBackend를 통해 동일 프로세스 내 Extensions 계층의 메모리(mSplitRules)에 즉시 캐싱됩니다(통상 앱 초기화 시점에 1회 호출). 이후 액티비티가 시작될 때도 인프로세스 메모리 탐색으로 분할 여부를 빠르게 판단합니다.
💡 더 유연한 동적 분할 제어: setSplitAttributesCalculator (Window 1.2+ / Ext 2+)
정적 SplitRule의 고정 비율 한계를 넘어, 람다 콜백을 통해 창 크기나 폴더블 자세(테이블탑 ➔ 상하 분할)에 따라 분할 속성을 런타임에 동적 계산합니다. 화면 변화 시 시스템 서버의 onTaskFragmentParentInfoChanged를 수신한 Extensions의 SplitPresenter.computeSplitAttributes()에서 인프로세스로 동기 실행됩니다.
🔗 공식 가이드: https://developer.android.com/develop/ui/views/layout/activity-embedding
1단계: 준비 플랫폼 바인딩

AndroidX & Extensions 계층 바인딩

AndroidX 계층 (앱 프로세스) androidx.window.embedding

개발자가 사용하는 RuleController 등 공개 API 제공. EmbeddingAdapter가 SplitRule을 하위 Extensions 계약 규격으로 자동 번역합니다.

Extensions 계층 (시스템 공유 라이브러리) androidx.window.extensions.embedding

기기 제조사(OEM)가 시스템 파티션에 탑재하며, SplitController가 SplitRule 캐싱과 런타임 분할 판정을 담당합니다.

🔬 빌드 타임 Stub (compileOnly) & 런타임 동적 마운트 (<uses-library>) 구조
  • 빌드 타임 (compileOnly): AndroidX는 로직 없는 인터페이스/Stub JAR만 참조하여 컴파일되므로, AAR/APK 내부에 OEM 클래스가 번들링되지 않습니다.
  • 패키징 (Manifest Merger): androidx.window:window AAR의 <uses-library android:name="androidx.window.extensions" android:required="false" />가 앱 Manifest로 자동 합성됩니다.
  • 런타임 (PathClassLoader): 지원 기기에서는 OS가 앱 프로세스 기동 시 /system_ext/framework/androidx.window.extensions.jar(실제 OEM 구현체)를 앱 클래스로더에 동적 마운트하여 OEM SplitController 구현체에 바인딩됩니다.
핵심 컨테이너 구조 단일 Task vs 다중 Task

핵심 컨테이너 구조: TaskFragment

Activity Embedding은 하나의 Task 안에서 화면을 쪼개어 배치하기 위해, Task와 Activity 사이에 TaskFragment라는 분할 구획(서브 스택) 컨테이너를 동적으로 생성합니다.

[전통적 Multi-Window] (다중 Task 분할) DisplayContent ├── Task 1 (최근 앱 타일 1) │ └── ActivityRecord (App A) └── Task 2 (최근 앱 타일 2) └── ActivityRecord (App B)
[Activity Embedding] (단일 Task 내부 분할) DisplayContent └── Task (최근 앱 타일 1개 유지) ├── TaskFragment 1 (Primary) │ └── ActivityRecord (Activity A) └── TaskFragment 2 (Secondary) └── ActivityRecord (Activity B)
비교 항목 전통적 Multi-Window (Split-Screen) Activity Embedding
태스크(Task) 경계 2개의 독립된 Task (서로 다른 최근 앱 카드) 단일 Task 내부 분할 (단일 앱 카드 유지)
주요 목적 서로 다른 두 앱 간의 멀티태스킹 (e.g. 유튜브 + 카톡) 단일 앱 내부의 대화면 레이아웃 최적화 (List-Detail)
제어권 주체 사용자 및 시스템 SystemUI (OS 주도) 앱 프로세스 및 개발자 (SplitRule 기반 App 주도)
내비게이션 각 창마다 독립 백스택, 개별 뒤로가기 통합 백스택 및 FinishBehavior 연계
핵심 결론: Activity Embedding은 다중 앱 멀티태스킹이 아니라, "단일 앱의 모듈식 대화면 UX 구현 도구"입니다.
하위 호환성 설계 임베딩 기능 위임 & 다형성

기능 위임과 다형성: Task extends TaskFragment

Android 12L부터 화면 분할 및 윈도우 제어 책임을 분할 컨테이너인 TaskFragment에 위임하여 하위 호환성과 유연성을 동시에 확보했습니다.

[레거시 일반 앱: 분할 미사용] Task (스스로 하나의 TaskFragment로 동작) └── ActivityRecord (직접 호스팅)
[Activity Embedding 앱: 대화면 분할] Task (최상위 호스트 - 분할을 TaskFragment에 위임) ├── TaskFragment 1 (Primary) ──▶ ActivityRecord └── TaskFragment 2 (Secondary) ──▶ ActivityRecord
역할 분담과 전담 위임 (Delegation)
  • Task (OS 작업 단위): Recents 카드 1개 유지, TaskId, taskAffinity, PIP
  • TaskFragment (화면 구획): 창 분할(Split), 상대적 Bounds, Multi-Resume 가시성 제어
Task도 TaskFragment이다 (다형성 & 하위 호환) 
// Android 11 ~ 12: Task가 직접 수납
class Task extends WindowContainer<WindowContainer> { ... }

// Android 12L+: TaskFragment 신설 & Task가 상속
class TaskFragment extends WindowContainer<WindowContainer> { ... }
class Task extends TaskFragment { ... }

Task extends TaskFragment 덕분에, 일반 앱에서도 별도의 래퍼 없이 Task 스스로 단일 TaskFragment로 동작합니다 (ATMS 내부에서 activity.getTaskFragment() 호출 시 직속 부모인 Task 반환).

2단계: 실행 가로채기 & 원자적 트랜잭션

startActivity 가로채기와 4단계 파이프라인

개발자는 평소대로 표준 startActivity(intent)를 호출할 뿐이며, 이 실행 과정에서 AndroidX 계층은 개입하지 않고 Extensions 계층이 런타임에 호출을 가로챕니다.

1단계 (SplitRule 캐싱): 앱 시작 시 mSplitRules에 등록 완료 (IPC 없음)
2단계 (가로채기 & 조건 평가): Instrumentation.execStartActivity() 직전, Extensions의 ActivityStartMonitor.onStartActivity()가 가로챔 ➔ SplitController가 SplitRule 대조 ➔ SplitPresenter가 윈도우 크기(minWidthDp) 실시간 평가 ➔ 타깃 컨테이너 토큰(KEY_LAUNCH_TASK_FRAGMENT_TOKEN) 주입
3단계 (원자적 WCT 패키징): TaskFragmentOrganizer가 컨테이너 생성·Bounds·인접 관계를 WindowContainerTransaction (WCT)으로 일괄 묶어 단 1회의 바인더 IPC로 전송 (화면 깜빡임·찢어짐 방지)
4단계 (트랜잭션 실행 & 라우팅): System Server (ATMS)의 TaskFragmentOrganizerController가 WCT를 원자적으로 실행해 계층 트리를 구성 ➔ ActivityStarter가 새 액티비티를 해당 TaskFragment 안으로 직접 라우팅
Window 1.4+ / Ext 8 런타임 직접 제어

1.4+ 런타임 직접 제어: 스택 & Overlay

미리 등록된 SplitRule에 맡기지 않고 런타임에 직접 분기 결정을 내릴 수 있도록, startActivity 옵션에 타깃 스택이나 오버레이를 주입하여 등록된 SplitRule 평가를 건너뛰는(Bypass) 메커니즘이 추가되었습니다.

① 타깃 스택 직접 지정 (setLaunchingActivityStack)
val options = ActivityOptions.makeBasic()
    .setLaunchingActivityStack(context, targetActivityStack)
    .toBundle()
startActivity(intent, options)

👉 ActivityStartMonitor가 번들 내 KEY_ACTIVITY_STACK_TOKEN을 확인하여 플랫폼 키로 변환한 뒤, SplitRule 평가 없이 조기 반환(Early Return)하여 시스템 서버로 넘깁니다.

② Overlay TaskFragment 플로팅 (setOverlayCreateParams)
val overlayParams = OverlayCreateParams.Builder()
    .setTag("SIDE_PANEL_TAG")
    .setOverlayAttributes(overlayAttributes)
    .setAssociateLaunchingActivity(true)
    .build()

val options = ActivityOptions.makeBasic()
    .setOverlayCreateParams(context, overlayParams)
    .toBundle()
startActivity(intent, options)

👉 기존 Split 화면 크기를 줄이지 않고 그 위에 최상단 Z-Order로 드로어/모달을 띄우며, KEY_OVERLAY_TAG 감지 시 createOrUpdateOverlayTaskFragmentIfNeeded()로 직행합니다.

보안 및 신뢰 경계 Same-UID & Cross-UID

보안 및 신뢰 경계

임의의 악의적 앱이 다른 은행 앱이나 로그인 화면을 자신의 창 안에 임베딩할 수 있다면 클릭재킹(Clickjacking), 탭재킹 및 피싱 공격이 가능해집니다.

🛡️ 기본 원칙: Same-UID 샌드박싱

OS는 기본적으로 동일한 UID(동일 패키지 및 동일 서명)를 가진 액티비티만 호스트 앱이 관리하는 TaskFragment(동일 Task) 내 임베딩을 허용합니다. 권한 없는 외부 앱의 임베딩 시도는 플랫폼 레벨에서 차단됩니다.

🤝 Cross-UID 신뢰 임베딩 조건

서로 다른 앱 간 분할 임베딩이 필요한 경우, 타깃 앱 매니페스트에 knownActivityEmbeddingCerts(호스트 앱의 인증서 SHA-256 서명값)를 명시하고 allowCrossUidActivityEmbedding="true"를 부여해야만 허용됩니다.

ATMS 검증: 시스템 서버(ATMS)의 ActivityStarter는 액티비티가 TaskFragment에 attach될 때마다 인증서 일치 여부를 원자적으로 검증합니다.
Z-Order & Top Activity Multi-Resume

Z-Order 판정과 Top Activity 역순 탐색

분할 화면에서는 좌우 두 액티비티가 모두 RESUMED 상태(Multi-Resume)입니다. 시스템은 어느 액티비티를 최상위(Top)로 판정할까요?

Task mChildren 컨테이너 리스트: Index 0: [ TaskFragment Primary (List) ] Index 1: [ TaskFragment Secondary (Detail) ] <-- pairedPosition + 1 로 삽입됨 (Top) ATMS 최상위 탐색 알고리즘: for (int i = mChildren.size() - 1; i >= 0; --i) { <-- 역순 탐색 (Top-Down Search) // 가장 먼저 발견되는 Secondary(Detail)가 시스템의 Top Activity로 확정 }
Intent Flag 영향:
Task 레벨에서 FLAG_ACTIVITY_SINGLE_TOP 호출 시, 시스템은 역순 탐색으로 발견된 Secondary(Detail)를 Top Activity로 판단하여 onNewIntent()를 전달합니다.
생명주기 및 연쇄 종료 3대 FinishBehavior

Activity Finish와 3대 FinishBehavior

한쪽 액티비티가 finish()될 때 반대편 액티비티를 어떻게 처리할지는 SplitRule.FinishBehavior로 제어합니다.

정책 (FinishBehavior) 동작 방식 대표 권장 시나리오
FINISH_NEVER 자신만 종료되고 상대방 컨테이너는 유지됨 상세 창을 닫아도 목록(List)은 계속 유지되어야 할 때 (기본값)
FINISH_ALWAYS 자신이 종료되면 인접한 상대방도 무조건 함께 종료 로그인 세션 종료, 결제 완료 등 두 화면이 완전히 한 몸일 때
FINISH_ADJACENT 자신이 종료될 때 인접 컨테이너가 살아있을 때만 연쇄 종료 단독 전체화면으로 전환된 경우에는 상대방을 닫지 않아야 할 때
4단계 Finish 파이프라인:
App finish() ➔ Extensions onTaskFragmentVanished() ➔ Frameworks WCT 연쇄 트랜잭션 ➔ ATMS 일괄 정리.
플랫폼 엔지니어링 패턴 ATMS & WCT

Frameworks & ATMS 4대 핵심 패턴

1. 원자적 배치 트랜잭션 (WindowContainerTransaction)

창 생성·크기 변경·액티비티 이동 연산을 단일 Binder IPC로 일괄 전송하여 단일 레이아웃 패스(Single Layout Pass)로 처리하고 화면 깜빡임을 방지합니다.

2. 불투명 토큰 기반 원격 제어 (TaskFragmentOrganizer)

시스템 서버의 창 객체를 직접 노출하지 않고 IBinder fragmentToken만 앱에 부여하며, 매 요청 시 호출 프로세스의 소유권(UID)을 검증합니다.

3. 컨테이너 라우팅 가로채기 (KEY_LAUNCH_TASK_FRAGMENT_TOKEN)

ActivityStarter가 인텐트 옵션의 토큰을 감지하면 기본 스택 배치를 우회하고 isAllowedToEmbedActivity() 보안 검증 후 타깃 TaskFragment로 직접 배정합니다.

4. 역방향 피드백 루프 (TaskFragmentParentInfo)

시스템 서버는 SplitRule을 알지 못합니다. 화면 회전·폴더블 변경 시 ATMS는 변경된 치수만 앱으로 통보하고, 앱의 SplitPresenter가 분할 여부를 판단해 WCT로 재배치합니다.
