Part 1. Intro Android 12L+ / API 32~35 androidx.window 1.4+

Android Activity Embedding
내부 아키텍처 심층 분석

단일 태스크(Task) 내에서 여러 Activity를 분할(Split) 및 오버레이(Overlay) 배치하여 호스팅하는 안드로이드 OS 플랫폼과 Jetpack WindowManager의 통합 내부 동작 원리를 탐구합니다.

🎯 핵심 탐구 주제
  • SoC (관심사 분리): 모놀리식 단일 액티비티를 탈피한 독립 모듈화
  • TaskFragment: 단일 Task 내 독립 창 컨테이너 인프라
  • 3계층 파이프라인: AndroidX ➔ Extensions ➔ Frameworks ➔ ATMS
  • 1.4 런타임 제어: 타깃 스택 지정 & Overlay TaskFragment (Ext 8)
🏗️ 플랫폼 엔지니어링 패턴
  • Composite 패턴: Task extends TaskFragment의 하위 호환성
  • 원자적 트랜잭션: WindowContainerTransaction (WCT)
  • Z-Order & Multi-Resume: pairedPosition + 1 판정
  • 보안 경계: Cross-UID 인증서 샌드박싱
Part 1. Background 문제의식 및 철학

대화면과 관심사 분리(SoC)의 필요성

폴더블, 태블릿, 크롬북 및 자동차(AAOS) 등 와이드 디스플레이가 대중화되면서, 전통적인 스마트폰 1화면-1액티비티 모델의 한계가 명확해졌습니다.

❌ 기존 방식의 문제점: Fragment 거대화

하나의 액티비티 안에 ListFragment와 DetailFragment를 우겨넣는 방식은 액티비티가 수많은 뷰모델, 콜백, 네비게이션 책임을 홀로 떠안아 **모놀리식 God Object**로 전락하게 만듭니다. 독립적인 기능 모듈화가 불가능해집니다.

✅ Activity Embedding의 해법: 관심사 분리(SoC)

목록(List)과 상세(Detail)를 완전한 독립 Activity로 분리하고 각자의 생명주기, ViewModel, Intent 인터페이스를 보존합니다. OS가 두 액티비티를 1개 화면 안에 나란히 호스팅해 줍니다.

💡 모듈형 아키텍처의 완성:
개발자는 기존 폰용 액티비티 코드와 매니페스트를 1줄도 수정하지 않고, 외부에서 선언한 규칙(SplitRule)만으로 대화면 멀티페인 레이아웃을 완성할 수 있습니다.
Part 1. Core Concept Android 12L 혁신

TaskFragment의 탄생: 단일 Task 내 독립 창 컨테이너

안드로이드 역사상 가장 큰 윈도우 관리 인프라의 변화는 Android 12L(API 32)의 TaskFragment 도입입니다.

[기존 Android 1.0 ~ 12] [Android 12L+ Activity Embedding] Task (1개 창 = 전체화면) Task (단일 최근 앱 카드, 단일 TaskId) └── ActivityRecord ├── TaskFragment A [Bounds: 좌측 40%] │ └── ActivityRecord (ListActivity) └── TaskFragment B [Bounds: 우측 60%] └── ActivityRecord (DetailActivity)
🔒 사용자 경험의 통일성

사용자 입장에서 두 화면은 분리된 창이 아니라 단 하나의 앱 카드(Recent Task)로 동작합니다. 앱 전환기에서 1개로 묶여 이동합니다.

📐 독립적인 창 컨테이너

OS 내부적으로는 각 TaskFragment가 독립된 Bounds, Configuration(화면 방향/크기), WindowContainer 계층을 가져 액티비티가 독립적으로 렌더링됩니다.

Part 2. Architecture 3-Tier Stack

Activity Embedding 3계층 아키텍처

Activity Embedding은 개발자 라이브러리부터 OS 시스템 서버까지 명확하게 분리된 3계층을 통해 동작합니다.

1. AndroidX 계층 (앱 프로세스) androidx.window.embedding

개발자 대면 API(RuleController, OverlayController). 고수준 규칙을 정의하고 하위 계층으로 전달합니다.

2. Extensions 계층: WindowManager Extensions (앱 프로세스) androidx.window.extensions.embedding

"런타임 두뇌": OEM이 기기 폼팩터에 맞춰 플랫폼 라이브러리로 제공. startActivity를 가로채 실시간 분할 조건을 판정합니다.

3. Frameworks 계층: Framework Core Client (앱 프로세스) android.window

TaskFragmentOrganizer가 컨테이너 조작 명령들을 원자적 WindowContainerTransaction (WCT)으로 패키징하여 시스템 서버(ATMS)로 IPC 전송합니다.

Part 2. Preparation IPC 최적화

[1단계: 준비] 규칙(Rule) 등록과 1회성 바인딩

앱 시작 시 RuleController를 통해 어떤 액티비티 쌍을 어떻게 쪼갤지 선언적으로 등록합니다.

val splitPairRule = SplitPairRule.Builder(filterSet)
    .setMinWidthDp(600)                        // 화면 폭 600dp 이상일 때만 분할
    .setDefaultSplitAttributes(
        SplitAttributes.Builder()
            .setSplitType(SplitAttributes.SplitType.ratio(0.4f)) // 4:6 분할
            .setLayoutDirection(SplitAttributes.LayoutDirection.LEFT_TO_RIGHT)
            .build()
    )
    .setFinishPrimaryWithSecondary(SplitRule.FinishBehavior.NEVER)
    .build()

RuleController.getInstance(context).setRules(setOf(splitPairRule))
⚡ 핵심 IPC 최적화 원리:
규칙 등록은 `startActivity` 호출마다 일어나는 것이 아닙니다. 앱 초기화 시점에 EmbeddingBackend가 Extensions 계층으로 단 1회만 전달하여 메모리에 캐싱(mSplitRules)합니다. 따라서 이후의 액티비티 실행 시 불필요한 IPC 오버헤드가 전혀 발생하지 않습니다.
Part 3. Execution Pipeline 런타임 흐름

[2단계: 실행] startActivity 4단계 파이프라인

개발자는 평소대로 표준 startActivity(intent)를 호출할 뿐이지만, 내부에서는 정교한 4단계 가로채기가 발생합니다.

[Step 1. App Call] 개발자가 startActivity(intent) 호출 (AndroidX 개입 없음) │ [Step 2. Intercept] Extensions의 ActivityStartMonitor.onStartActivity() 가로채기 ➔ SplitController가 캐싱된 mSplitRules 대조 ➔ SplitPresenter가 현재 윈도우 크기(minWidthDp) 실시간 평가 │ [Step 3. Packaging] TaskFragmentOrganizer가 조작 명령들을 원자적 WindowContainerTransaction(WCT)으로 묶음 │ [Step 4. Execution] ATMS(ActivityTaskManagerService)로 1회 일괄 전송 ➔ 단일 트랜잭션 내에서 TaskFragment 생성 및 배치 완료!
👉 무간섭 원칙 (Transparency): 기존 앱 코드에는 WindowManager 전용 옵션이나 특수 API 호출이 들어가지 않으므로 일반 폰과 대화면 기기에서 완벽한 바이너리 호환성을 가집니다.
Part 3. Runtime Control Window 1.4+ / Ext 8

타깃 스택 직접 지정 (setLaunchingActivityStack)

Window 1.4부터는 사전 등록된 SplitRule에 의존하지 않고, 개발자가 런타임에 직접 타깃 컨테이너를 지정하여 분기할 수 있는 명령형 API가 추가되었습니다.

// 타깃 ActivityStack을 ActivityOptions(Bundle)에 패키징하여 실행:
val options = ActivityOptions.makeBasic().toBundle().apply {
    setLaunchingActivityStack(context, targetActivityStack)
}
startActivity(intent, options)
⚡ SplitRule 평가 우회 (Bypass)

번들에 KEY_ACTIVITY_STACK_TOKEN이 들어있으면, Extensions 계층은 등록된 SplitRule 평가를 아예 건너뛰고 해당 스택으로 직행합니다.

🚀 조기 반환 (Early Return)

ActivityStartMonitor가 플랫폼 키(KEY_LAUNCH_TASK_FRAGMENT_TOKEN)로 즉시 변환한 뒤 시스템 서버로 조기 반환하여 넘깁니다.

Part 3. Runtime Control Window 1.4+ / Ext 8 신규 핵심 기능

Overlay TaskFragment 플로팅 (setOverlayCreateParams)

Extension 8의 가장 혁신적인 변화는 기존 Split 화면을 리사이즈하지 않고 그 위에 최상단 Z-Order로 드로어/모달을 띄우는 기능입니다.

val overlayParams = OverlayCreateParams.Builder()
    .setTag("NAV_DRAWER_TAG")
    .setOverlayAttributes(
        OverlayAttributes.Builder()
            .setBounds(EmbeddingBounds(Alignment.LEFT, Dimension.ratio(0.75f), Dimension.DIMENSION_EXPANDED))
            .build()
    )
    .setAssociateLaunchingActivity(true) // 부모 액티비티 종료 시 오버레이 자동 정리
    .build()

val options = ActivityOptions.makeBasic().toBundle().apply {
    ActivityEmbeddingOptions.setOverlayCreateParams(this, overlayParams)
}
startActivity(intent, options)
동작 메커니즘 (SplitController.java):
KEY_OVERLAY_TAG가 감지되면 createOrUpdateOverlayTaskFragmentIfNeeded()가 실행되어 기존 동일 태그 컨테이너를 재사용하거나 최상단 레이어에 새 오버레이 TaskFragment를 원자적으로 생성합니다.
Part 3. System Server 플랫폼 내부

WCT 트랜잭션과 ATMS 계층 트리 배치

System Server(ActivityTaskManagerService)는 WCT를 수신하여 단 하나의 렌더링 패스 내에서 컨테이너 계층 트리를 구성합니다.

DisplayContent (물리 디스플레이) └── TaskDisplayArea └── Task (단일 최근 앱 엔트리) ├── TaskFragment 1 (Primary) [Bounds: (0,0) - (800,1600)] │ └── ActivityRecord (ListActivity) └── TaskFragment 2 (Secondary) [Bounds: (800,0) - (2000,1600)] └── ActivityRecord (DetailActivity)
⚡ 원자적 WCT (Atomic Transaction)

생성, 상대적 Bounds 설정, 인접 관계(adjacent) 설정이 1회의 바인더 호출로 처리되므로 중간 상태 노출이나 화면 깜빡임(Flicker)이 원천 차단됩니다.

🔄 TaskOrganizer와의 조화

시스템의 전체 윈도우 관리(SysUI)와 앱 내부의 창 분할(TaskFragmentOrganizer)이 서로 간섭 없이 완벽한 계층 분리를 달성합니다.

Part 4. Engineering Composite Pattern

하위 호환성의 비밀: Composite 패턴

안드로이드 프레임워크가 10년 넘게 축적된 시스템 코드를 깨뜨리지 않고 어떻게 TaskFragment를 도입했을까요?

WindowContainer (추상 기본 클래스) └── TaskFragment (창 경계 및 액티비티 호스팅 단위) ├── Task (TaskFragment를 상속! - Composite 패턴) │ └── TaskFragment 1, TaskFragment 2 ... └── TaskFragment (일반 임베딩 컨테이너) └── ActivityRecord
구조적 다형성 (Structural Polymorphism):
public class Task extends TaskFragment 구조 덕분에, ATMS 내부의 기존 코드(포커스 탐색, 백스택 탐색, 트랜지션 처리)는 대상을 TaskFragment 인터페이스로 동일하게 취급할 수 있습니다. 수십만 줄의 기존 시스템 코드를 수정하지 않고도 완벽한 하위 호환성을 달성했습니다.
Part 4. Engineering 핵심 설계 원칙

플랫폼 4대 핵심 아키텍처 패턴

1. Organizer 패턴 (TaskFragmentOrganizer)

시스템 서버에 갇혀 있던 윈도우 레이아웃 제어권을 시스템 권한 없이도 클라이언트 프로세스에 안전하게 위임(Delegation)합니다.

2. 원자적 트랜잭션 패턴 (WCT)

여러 컨테이너 변경 연산을 단일 IPC로 일괄 전송(Batching)하여 IPC 지연을 줄이고 화면 찢어짐/깜빡임을 방지합니다.

3. Composite 패턴 (Task extends TaskFragment)

단일 노드(TaskFragment)와 복합체(Task)를 동일한 추상화로 다루어 시스템 서버 전반의 호환성을 보장합니다.

4. 프록시 / 어댑터 패턴 (Extensions)

기기 제조사(OEM)별 하드웨어 특수성과 구글 Jetpack 라이브러리 간의 결합도를 낮추고 모듈식 업데이트를 가능하게 합니다.

Part 5. Lifecycle Multi-Resume & Z-Order

Z-Order 및 Top Activity 역순 탐색 알고리즘

분할 화면에서는 좌우 두 액티비티가 모두 RESUMED 상태(Multi-Resume)입니다. 그렇다면 시스템은 어느 액티비티를 '진짜 최상위(Top)'로 판정할까요?

Task mChildren 컨테이너 리스트: Index 0: [ TaskFragment Primary (List) ] Index 1: [ TaskFragment Secondary (Detail) ] <-- pairedPosition + 1 로 삽입됨 (Top) ATMS 탐색 알고리즘: for (int i = mChildren.size() - 1; i >= 0; --i) { <-- 역순 탐색 (Top-Down Search) // 가장 먼저 발견되는 Secondary(Detail)가 시스템의 공식 Top Activity로 확정! }
Intent Flag 영향:
Task 레벨에서 FLAG_ACTIVITY_SINGLE_TOP 호출 시, 시스템은 역순 탐색으로 발견된 Secondary(Detail)를 Top Activity로 판단하여 onNewIntent()를 전달합니다.
Part 5. Lifecycle 연쇄 종료

FinishBehavior 3가지 연쇄 종료 정책

한쪽 액티비티가 finish()될 때 반대편 액티비티를 어떻게 처리할지는 SplitRule.FinishBehavior로 제어합니다.

정책 (FinishBehavior) 동작 방식 대표 권장 시나리오
FINISH_NEVER 자신만 종료되고 상대방 컨테이너는 유지됨 상세 창을 닫아도 목록(List)은 계속 유지되어야 할 때 (기본값)
FINISH_ALWAYS 자신이 종료되면 인접한 상대방도 무조건 함께 종료 로그인 세션 종료, 결제 완료 등 두 화면이 완전히 한 몸일 때
FINISH_ADJACENT 자신이 종료될 때 인접 컨테이너가 살아있을 때만 연쇄 종료 단독 전체화면으로 전환된 경우에는 상대방을 닫지 않아야 할 때
파이프라인: App finish() ➔ Extensions onTaskFragmentVanished() ➔ WCT 연쇄 트랜잭션 ➔ ATMS 일괄 정리.

Part 6. Comparison 아키텍처 비교

전통적 Multi-Window vs Activity Embedding

두 기술은 모두 화면을 분할하지만, 설계 목표와 태스크 경계(Task Boundary)가 근본적으로 다릅니다.

비교 항목 전통적 Multi-Window (Split-Screen) Activity Embedding
태스크(Task) 경계 2개의 독립된 Task (서로 다른 최근 앱 카드) 단일 Task 내부 분할 (단일 앱 카드)
주요 목적 서로 다른 두 앱 간의 멀티태스킹 (e.g. 유튜브 + 카톡) 단일 앱 내부의 대화면 레이아웃 최적화 (List-Detail)
제어권 주체 사용자 및 시스템 SystemUI (OS 주도) 앱 프로세스 및 개발자 (App 주도)
내비게이션 각 창마다 독립 백스택, 개별 뒤로가기 통합 백스택 및 FinishBehavior 연계
결론: Activity Embedding은 다중 앱 멀티태스킹이 아니라, "단일 앱의 모듈식 대화면 UX 구현 도구"입니다.
Part 6. Security Trust Boundary

보안 및 Cross-UID 신뢰 경계 (Security & Sandbox)

임의의 앱이 다른 앱의 액티비티를 마음대로 창 안에 임베딩할 수 있다면 클릭재킹(Clickjacking)과 피싱 등 심각한 보안 취약점이 발생합니다.

🛡️ 기본 원칙: Same-UID 샌드박싱

OS는 기본적으로 **동일한 UID(동일 앱/동일 서명)**를 가진 액티비티만 동일 TaskFragment 내 분할을 허용합니다. 권한 없는 외부 앱의 임베딩 시도는 차단됩니다.

🤝 Cross-UID 신뢰 임베딩 조건

서로 다른 앱 간 임베딩이 필요한 경우(e.g. 결제 모듈, SDK), 호스트 앱의 인증서 SHA-256을 타깃 앱의 매니페스트에 knownActivityEmbeddingCerts로 명시해야만 허용됩니다.

신뢰 경계: 시스템 서버(ATMS)는 액티비티가 TaskFragment에 attach될 때마다 인증서 일치 여부를 원자적으로 검증합니다.
Part 7. Summary Best Practices

종합 요약 및 대화면 UI 아키텍처 권장 가이드

📌 핵심 테이크어웨이 (Takeaways)
  • TaskFragment는 단일 Task 내 독립 컨테이너를 제공하는 안드로이드 윈도우의 혁신입니다.
  • 3계층 아키텍처로 무간섭(Zero-touch) 표준 startActivity 실행을 보장합니다.
  • Window 1.4 / Ext 8부터 타깃 스택 지정과 Overlay TaskFragment로 반응형 드로어 UX가 가능해졌습니다.
  • Composite 패턴을 통해 기존 10년 안드로이드 프레임워크와의 완벽한 하위 호환성을 이뤄냈습니다.
💡 실무 아키텍처 의사결정 기준
  • 레거시 멀티 액티비티 앱: 코드 재작성 없이 Activity Embedding으로 대화면 대응.
  • 신규 앱 / Jetpack Compose: 단일 Activity + Compose Adaptive (Canonical Layouts) 권장.
  • 반응형 드로어 UX: 좁은 화면(Detail 단독 시작) + 대화면(List-Detail 고정 Split) 구조 설계.
