Architecture Deep Dive Android 12L (API 32) & Android 13+ / AAOS androidx.window:window:1.3+

Android Activity Embedding
내부 아키텍처 심층 분석

Android 12L(API 32) 및 Android 13+와 Jetpack WindowManager가 단일 태스크(Task) 내에서 여러 Activity를 분할 배치(Split)하여 호스팅하는 내부 동작 원리를 탐구합니다. 진정한 모듈화, 패키지 간 관심사 분리(SoC, Separation of Concerns), 그리고 완성도 높은 대화면 멀티페인 레이아웃 구현 메커니즘을 상세히 다룹니다.

🎯 본 기술 분석의 핵심 탐구 축
  • 관심사 분리(SoC): AAOS 차량 설정과 헤드리스 서비스 간 멀티 APK 분할
  • 준비 ➔ 실행 파이프라인: 규칙 캐싱, 가로채기(Intercept), 원자적 WCT 패키징
  • 1.4 런타임 직접 제어: 타깃 스택 지정 & Overlay TaskFragment (Ext 8)
  • 하위 호환성: Task extends TaskFragment (기능 위임 & 다형성)
🔬 플랫폼 엔지니어링 & 런타임 제어
  • Multi-Resume & Z-Order: pairedPosition + 1 및 Top-Down 역순 탐색
  • Finish 연쇄 종료: 3대 SplitRule.FinishBehavior 파이프라인
  • 보안 경계: Same-UID 샌드박스 및 Cross-UID 인증서 서명 검증
  • Multi-Window 비교: 단일 Task vs 독립 Task 아키텍처 차이
Section 1 SoC 도입 배경 AAOS 환경

1. 개요 및 도입 배경: 와이드 디스플레이 환경에서의 관심사 분리(SoC)

Android Automotive OS (AAOS) 중앙 센터페시아 대화면 환경에서는 메인 차량 설정(Vehicle Settings) 앱이 런처 UI가 없는 음성 인식(Voice Recognition) 등 다양한 헤드리스 백그라운드 서비스들의 통합 진입점 역할을 담당합니다. 기존 단일 액티비티 구조는 관심사 분리(SoC)를 심각하게 저해하는 안티패턴을 초래합니다.

As-Is: 모놀리식 안티패턴 (SoC 위반)
┌─ AAOS 디스플레이 (Task: Vehicle Settings) ─────┐ │ ┌─ 카테고리 목록 ──┐ ┌─ 음성 설정 UI 및 DB ──┐ │ │ │ VehicleSettings │ │ ❌ VehicleSettings.apk│ │ │ │ .apk │ │ 에 직접 구현됨 (결합) │ │ │ └─────────────────┘ └────────────────────────┘ │ └────────────────────────────────────────────────┘ ▲▼ 취약한 IPC 동기화: ContentProvider / AIDL ┌─ 헤드리스 음성 인식 서비스 (VoiceService.apk) ─┐ └────────────────────────────────────────────────┘

⚠️ 도메인 경계 붕괴: 음성 서비스 수정 시 메인 차량 설정 앱을 재빌드/재배포해야 하는 강한 결합 발생.

To-Be: Activity Embedding 호스트 (깔끔한 SoC)
┌─ AAOS 디스플레이 (통합 태스크 컨테이너) ───────┐ │ ┌─ 카테고리 목록 ──┐ ┌─ VoiceSettingsActivity ─┐ │ │ │ TaskFragment 1 │ │ TaskFragment 2 │ │ │ │ (VehicleSettings│ │ (✅ VoiceService.apk │ │ │ │ .apk) │ │ 로부터 임베딩) │ │ │ └─────────────────┘ └────────────────────────┘ │ └────────────────────────────────────────────────┘ VoiceService.apk가 자체 Activity와 Service를 완전히 소유!

✅ 모듈식 호스트: 차량 설정 앱은 UI 셸 역할만 수행하고, 각 서비스 패키지가 자체 화면과 로직을 독립 소유.

💡 핵심 가치: 패키지 경계를 넘어서는 뷰 임베딩을 통해 기존 액티비티 코드 수정 없이 독자적인 생명주기와 독립적 배포 주기를 온전히 보장합니다.
Section 2 1단계: 준비 플랫폼 바인딩

2. 규칙(Rule) 등록과 플랫폼 바인딩 (AndroidX & Extensions)

AndroidX 계층 (앱 프로세스) androidx.window.embedding

개발자가 사용하는 RuleController 등 공개 API 제공. EmbeddingAdapter가 고수준 규칙을 하위 Extensions 계약 규격으로 자동 번역합니다.

Extensions 계층 (시스템 공유 라이브러리) androidx.window.extensions.embedding

"런타임 의사결정의 두뇌". 기기 제조사(OEM)가 시스템 파티션에 탑재하며, SplitController가 규칙 캐싱과 런타임 분할 판정을 담당합니다.

🔬 빌드 타임 Stub (compileOnly) & 런타임 동적 마운트 (<uses-library>)의 비밀
  • 빌드 타임 (compileOnly): AndroidX는 로직 없는 순수 인터페이스/Stub JAR만 참조하여 컴파일되므로, AAR/APK 내부에 OEM 클래스가 번들링되지 않습니다.
  • 패키징 (Manifest Merger): androidx.window:window AAR의 <uses-library android:name="androidx.window.extensions" android:required="false" />가 앱 Manifest로 자동 합성됩니다.
  • 런타임 (PathClassLoader): 지원 기기에서는 OS가 앱 프로세스 기동 시 /system_ext/framework/androidx.window.extensions.jar(실제 OEM 구현체)를 앱 클래스로더에 동적 마운트하여 진짜 `SplitController`에 안전하게 바인딩됩니다.
Section 2 Zero IPC 인메모리 캐싱

RuleController 등록과 인메모리 캐싱 (Zero IPC)

val splitPairRule = SplitPairRule.Builder(filterSet)
    .setMinWidthDp(600)
    .setDefaultSplitAttributes(
        SplitAttributes.Builder()
            .setSplitType(SplitAttributes.SplitType.ratio(0.4f))
            .setLayoutDirection(SplitAttributes.LayoutDirection.LEFT_TO_RIGHT)
            .build()
    )
    .setFinishPrimaryWithSecondary(SplitRule.FinishBehavior.NEVER)
    .build()

RuleController.getInstance(context).setRules(setOf(splitPairRule))
⚡ 핵심 원리: 시스템 서버 통신 0회 (Zero IPC 인메모리 캐싱):
규칙 등록 시 시스템 서버(ATMS)와의 IPC 통신은 0회입니다! 앱 초기화 시점에 EmbeddingBackend를 통해 동일 프로세스 내 Extensions 계층의 메모리(mSplitRules)에만 즉시 캐싱됩니다. 이후 실제 액티비티가 시작될 때도 OS에 묻지 않고 인프로세스 메모리 탐색만으로 즉시 분할 여부를 판단합니다.
Section 3 핵심 컨테이너 구조

3. 핵심 컨테이너 구조: Task와 Activity 사이의 TaskFragment

Activity Embedding은 하나의 Task 안에서 화면을 쪼개어 배치하기 위해, Task와 Activity 사이에 TaskFragment라는 분할 구획(서브 스택) 컨테이너를 동적으로 생성합니다.

[전통적 Multi-Window] (다중 Task 분할) [Activity Embedding] (단일 Task 내부 분할) DisplayContent DisplayContent ├── Task 1 (최근 앱 타일 1) └── Task (최근 앱 타일 1개로 통일!) │ └── ActivityRecord (App A) ├── TaskFragment 1 (Primary) └── Task 2 (최근 앱 타일 2) │ └── ActivityRecord (Activity A) └── ActivityRecord (App B) └── TaskFragment 2 (Secondary) └── ActivityRecord (Activity B)
Multi-Window와의 결정적 차이:
전통적 멀티윈도우는 OS가 서로 다른 2개의 Task를 나란히 타일링하는 반면, Activity Embedding은 단 1개의 Task 내부를 TaskFragment로 쪼개어 쓰므로 최근 앱(Recents)에서도 1개의 통합 카드로 유지되며 동일한 TaskId와 TaskAffinity를 공유합니다.
Section 3 2단계: 실행

startActivity 가로채기와 4단계 파이프라인

개발자는 평소대로 표준 startActivity(intent)를 호출할 뿐이며, 이 실행 과정에서 AndroidX 계층은 개입하지 않고 Extensions 계층이 런타임에 호출을 가로챕니다.

1단계 (규칙 캐싱): 앱 시작 시 mSplitRules에 등록 완료 (IPC 없음)
2단계 (가로채기 & 조건 평가): Instrumentation.execStartActivity() 직전, Extensions의 ActivityStartMonitor.onStartActivity()가 가로챔 ➔ SplitController가 규칙 대조 ➔ SplitPresenter가 윈도우 크기(minWidthDp) 실시간 평가 ➔ 타깃 컨테이너 토큰(KEY_LAUNCH_TASK_FRAGMENT_TOKEN) 주입
3단계 (원자적 WCT 패키징): TaskFragmentOrganizer가 컨테이너 생성/바운드 설정을 WindowContainerTransaction (WCT)으로 일괄 패키징
4단계 (트랜잭션 실행 & 라우팅): System Server (ATMS)의 TaskFragmentOrganizerController가 WCT 실행 ➔ ActivityStarter가 새 액티비티를 해당 TaskFragment 안으로 직접 라우팅
Section 3 Window 1.4+ / Ext 8 런타임 직접 제어

⚡ 1.4+ 런타임 직접 제어: 타깃 스택 지정 & Overlay TaskFragment

미리 등록된 규칙에 맡기지 않고 런타임에 직접 분기 결정을 내릴 수 있도록, startActivity 옵션에 타깃 스택이나 오버레이를 주입하여 등록된 SplitRule 평가를 건너뛰는(Bypass) 메커니즘이 추가되었습니다.

① 타깃 스택 직접 지정 (setLaunchingActivityStack)
val options = ActivityOptions.makeBasic().toBundle().apply {
    setLaunchingActivityStack(context, targetActivityStack)
}
startActivity(intent, options)

👉 ActivityStartMonitor가 번들 내 KEY_ACTIVITY_STACK_TOKEN을 확인하여 플랫폼 키로 변환한 뒤, 규칙 평가 없이 즉시 조기 반환(Early Return)하여 시스템 서버로 넘깁니다.

② Overlay TaskFragment 플로팅 (setOverlayCreateParams)
val overlayParams = OverlayCreateParams.Builder()
    .setTag("SIDE_PANEL_TAG")
    .setOverlayAttributes(overlayAttributes)
    .setAssociateLaunchingActivity(true)
    .build()

val options = ActivityOptions.makeBasic().toBundle().apply {
    ActivityEmbeddingOptions.setOverlayCreateParams(this, overlayParams)
}
startActivity(intent, options)

👉 기존 Split 화면 크기를 줄이지 않고 그 위에 최상단 Z-Order로 드로어/모달을 띄우며, KEY_OVERLAY_TAG 감지 시 createOrUpdateOverlayTaskFragmentIfNeeded()로 직행합니다.

Section 3 플랫폼 내부 트리 원자적 트랜잭션

원자적 WCT(WindowContainerTransaction) 패키징 & ATMS 트리

WCT (WindowContainerTransaction)는 창 컨테이너(Task, TaskFragment 등)의 생성·크기 지정·인접 설정을 단일 바인더 IPC로 묶어 전송하는 Frameworks 계층의 일괄 트랜잭션 객체(android.window)입니다. 시스템 서버(ATMS)는 전달받은 WCT를 원자적으로 처리하여 계층 트리를 구성합니다.

DisplayContent (물리 디스플레이) └── TaskDisplayArea └── Task (단일 최근 앱 엔트리) ├── TaskFragment 1 (Primary) [Bounds: (0,0) - (800,1600)] │ └── ActivityRecord (Activity A) └── TaskFragment 2 (Secondary) [Bounds: (800,0) - (2000,1600)] └── ActivityRecord (Activity B)
⚡ 왜 WCT(원자적 트랜잭션)인가?
컨테이너 생성, 상대적 Bounds 설정, 인접 관계(adjacent) 설정이 단 1회의 바인더 IPC로 일괄 처리됩니다. 따라서 좌우 화면이 어긋나게 렌더링되거나 중간 상태가 노출되는 화면 깜빡임(Flickering)과 찢어짐(Tearing)이 원천 차단됩니다.
Section 4 하위 호환성 설계 임베딩 기능 위임 & 다형성

4. 계층 구조의 진화: Task에서 TaskFragment로의 기능 위임

기존 Task의 거대한 책임 중 화면 분할(Embedding), 윈도우 Bounds, 액티비티 가시성/생명주기 제어 책임을 전용 경량 컨테이너인 TaskFragment에 깔끔하게 위임했습니다.

[레거시 일반 앱: 분할 미사용] [Activity Embedding 앱: 대화면 분할] Task (스스로 하나의 TaskFragment로 동작) Task (최상위 호스트 - 분할 책임을 TaskFragment에 위임) └── ActivityRecord (직접 호스팅) ├── TaskFragment 1 (Primary) ──▶ ActivityRecord └── TaskFragment 2 (Secondary) ──▶ ActivityRecord
1. 임베딩 기능의 전담 위임 (Delegation)

창 분할(Split), 상대적 Bounds, Multi-Resume 가시성 제어는 TaskFragment가 전담합니다.

  • Task: Recents 카드, TaskId, taskAffinity, PIP (OS 작업 관리)
  • TaskFragment: 화면 분할, Bounds 비율, 윈도우 렌더링 (뷰포트 구획)
2. Task도 TaskFragment이다 (다형성 & 하위 호환) 
// Android 11 ~ 12: Task가 직접 수납
class Task extends WindowContainer<WindowContainer> { ... }

// Android 12L+: TaskFragment 신설 & Task가 상속
class TaskFragment extends WindowContainer<WindowContainer> { ... }
class Task extends TaskFragment { ... }

Task extends TaskFragment 덕분에, 일반 앱에서도 별도의 래퍼 없이 Task 스스로 단일 TaskFragment로 동작합니다 (ATMS 내부에서 activity.getTaskFragment() 호출 시 직속 부모인 Task 반환).

Section 4 선언적 규칙 모델

선언적 규칙 기반(Rule-Based) 아키텍처의 의의

1. 무간섭성 (Zero-touch Modularity)

임베딩되는 피호출 액티비티는 자신이 분할 화면으로 뜨는지 전체화면으로 뜨는지 알 필요가 없습니다. 기존의 표준 startActivity() 호출 방식을 그대로 유지하면서 외부 선언 규칙만으로 뷰를 재구성합니다.

2. 환경 적응형 분할 (Adaptive Layout)

폴더블 기기를 펼치거나(Unfold), 화면을 회전하거나, 멀티윈도우 크기를 조절할 때 시스템이 minWidthDp를 실시간으로 재평가하여 분할 모드와 일반 스택 모드를 동적으로 자동 전환합니다.

아키텍처적 가치: UI 분할 정책을 개별 Activity 내부 로직과 완전히 분리함으로써, 화면 크기 변화에 유연하게 대응하는 선언적 시스템을 구축했습니다.
Section 5 보안 및 신뢰 경계

5. 보안 및 신뢰 경계 (Security & Trust Boundary)

임의의 악의적 앱이 다른 은행 앱이나 로그인 화면을 자신의 창 안에 임베딩할 수 있다면 클릭재킹(Clickjacking), 탭재킹 및 피싱 공격이 가능해집니다.

🛡️ 기본 원칙: Same-UID 샌드박싱

OS는 기본적으로 **동일한 UID(동일 패키지 및 동일 서명)**를 가진 액티비티만 동일 TaskFragment 내 임베딩을 허용합니다. 권한 없는 외부 앱의 임베딩 시도는 플랫폼 레벨에서 차단됩니다.

🤝 Cross-UID 신뢰 임베딩 조건

서로 다른 앱 간 분할 임베딩이 필요한 경우, 타깃 앱 매니페스트에 knownActivityEmbeddingCerts(호스트 앱의 인증서 SHA-256 서명값)를 명시하고 allowCrossUidActivityEmbedding="true"를 부여해야만 허용됩니다.

ATMS 검증: 시스템 서버(ATMS)의 ActivityStarter는 액티비티가 TaskFragment에 attach될 때마다 인증서 일치 여부를 원자적으로 검증합니다.
부록 A 기술 비교

부록 A. 전통적 Multi-Window vs Activity Embedding

비교 항목 전통적 Multi-Window (Split-Screen) Activity Embedding
태스크(Task) 경계 2개의 독립된 Task (서로 다른 최근 앱 카드) 단일 Task 내부 분할 (단일 앱 카드)
주요 목적 서로 다른 두 앱 간의 멀티태스킹 (e.g. 유튜브 + 카톡) 단일 앱 내부의 대화면 레이아웃 최적화 (List-Detail)
제어권 주체 사용자 및 시스템 SystemUI (OS 주도) 앱 프로세스 및 개발자 (App 주도)
내비게이션 각 창마다 독립 백스택, 개별 뒤로가기 통합 백스택 및 FinishBehavior 연계
결론: Activity Embedding은 다중 앱 멀티태스킹이 아니라, "단일 앱의 모듈식 대화면 UX 구현 도구"입니다.
부록 B Z-Order & Top Activity

부록 B. Multi-Resume 환경의 Top Activity 판정과 Z-Order

분할 화면에서는 좌우 두 액티비티가 모두 RESUMED 상태(Multi-Resume)입니다. 그렇다면 시스템은 어느 액티비티를 '진짜 최상위(Top)'로 판정할까요?

Task mChildren 컨테이너 리스트: Index 0: [ TaskFragment Primary (List) ] Index 1: [ TaskFragment Secondary (Detail) ] <-- pairedPosition + 1 로 삽입됨 (Top) ATMS 최상위 탐색 알고리즘: for (int i = mChildren.size() - 1; i >= 0; --i) { <-- 역순 탐색 (Top-Down Search) // 가장 먼저 발견되는 Secondary(Detail)가 시스템의 공식 Top Activity로 확정! }
Intent Flag 영향:
Task 레벨에서 FLAG_ACTIVITY_SINGLE_TOP 호출 시, 시스템은 역순 탐색으로 발견된 Secondary(Detail)를 Top Activity로 판단하여 onNewIntent()를 전달합니다.
부록 C 생명주기 및 연쇄 종료

부록 C. 분할 화면에서의 Activity Finish 및 연쇄 종료 정책

한쪽 액티비티가 finish()될 때 반대편 액티비티를 어떻게 처리할지는 SplitRule.FinishBehavior로 제어합니다.

정책 (FinishBehavior) 동작 방식 대표 권장 시나리오
FINISH_NEVER 자신만 종료되고 상대방 컨테이너는 유지됨 상세 창을 닫아도 목록(List)은 계속 유지되어야 할 때 (기본값)
FINISH_ALWAYS 자신이 종료되면 인접한 상대방도 무조건 함께 종료 로그인 세션 종료, 결제 완료 등 두 화면이 완전히 한 몸일 때
FINISH_ADJACENT 자신이 종료될 때 인접 컨테이너가 살아있을 때만 연쇄 종료 단독 전체화면으로 전환된 경우에는 상대방을 닫지 않아야 할 때
4단계 Finish 파이프라인:
App finish() ➔ Extensions onTaskFragmentVanished() ➔ Frameworks WCT 연쇄 트랜잭션 ➔ ATMS 일괄 정리.
부록 D 플랫폼 엔지니어링 패턴

부록 D. Frameworks & System Server 4대 핵심 패턴

1. Organizer 패턴 (TaskFragmentOrganizer)

시스템 서버에 갇혀 있던 윈도우 레이아웃 제어권을 시스템 권한 없이도 클라이언트 프로세스에 안전하게 위임(Delegation)합니다.

2. 원자적 트랜잭션 패턴 (WCT)

여러 컨테이너 변경 연산을 단일 IPC로 일괄 전송(Batching)하여 IPC 지연을 줄이고 화면 찢어짐/깜빡임을 방지합니다.

3. 기능 위임과 다형성 (Task extends TaskFragment)

Task의 거대한 책임 중 화면 분할(Embedding)과 가시성 제어를 TaskFragment에 깔끔하게 위임하고 상속을 통해 100% 하위 호환성을 보장합니다.

4. 프록시 / 어댑터 패턴 (Extensions)

기기 제조사(OEM)별 하드웨어 특수성과 구글 Jetpack 라이브러리 간의 결합도를 낮추고 모듈식 업데이트를 가능하게 합니다.
