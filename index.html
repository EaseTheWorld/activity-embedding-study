Android Activity Embedding Under the Hood

A comprehensive architectural exploration of how Android (12L+) and Jetpack WindowManager coordinate to host and embed multiple activities side-by-side inside a single task—enabling true modularity, cross-app separation of concerns, and clean multi-pane layouts.

Platform: Android 12L (API 32) & Android 13+ / AAOS
Library: androidx.window:window:1.3+

1. Overview & Motivation: Separation of Concerns on Wide Displays

On large fixed screens such as Android Automotive OS (AAOS) center displays, applications commonly adopt a fixed wide two-pane (List-Detail) layout. A central Vehicle Settings application acts as the user-facing hub for diverse vehicle domains—from display and connectivity to headless background services like Voice Recognition.

Because headless system services lack their own launcher UI or top-level window, conventional architectures force the host settings app into a severe architectural anti-pattern that violates Separation of Concerns (SoC):

The Monolithic Anti-Pattern Violated SoC

Host App Implements External Subsystem UI: Because the headless voice recognition service has no standalone entry UI, the Vehicle Settings app is forced to build its configuration screens, maintain its settings keys, and synchronize values over ContentProvider or AIDL.

Architectural Flaw: Domain boundaries collapse. Any feature update, UI tweak, or schema modification in the Voice Recognition service forces code churn, re-testing, and redeployment of the central Vehicle Settings app.

The Activity Embedding Solution Clean Modular Host

Subsystems Own Their Own UI: The Voice Recognition package ships its own self-contained VoiceSettingsActivity inside its own APK. The Vehicle Settings app simply embeds it into the right detail pane.

Architectural Gain: True Separation of Concerns. The voice team owns its UI, business logic, and storage. The driver experiences a single, seamless settings app, while the underlying codebases and release cycles remain 100% independent.

Why In-App Fragments or Compose Cannot Solve This Across Packages

Within a single application package, Fragment transactions or Compose components handle list-detail navigation easily. However, Fragments and Views cannot cross APK or process boundaries without massive shared-library bloat or fragile remote views. Activity Embedding operates at the WindowManager container and compositor layer, allowing completely separate APKs—verified via OEM certificates (android:knownActivityEmbeddingCerts)—to securely render side-by-side inside a single unified window task.

3. End-to-End Execution Sequence

The activity embedding lifecycle operates across three primary stages. Every operation coordinates across the 4 architectural layers introduced earlier:

1

1. Setting Rule with RuleController

At application startup, rules are registered and bound to the process:

RuleController.getInstance(context).setRules(setOf(splitPairRule));
  • Layer 1: App / AndroidX The app creates high-level rules (e.g. SplitPairRule) and calls RuleController.setRules(). EmbeddingAdapter converts them into OEM contract interfaces.
  • Layer 2: OEM Extension SplitController.setEmbeddingRules() receives the rules and attaches an ActivityStartMonitor to the app's Instrumentation instance (via instrumentation.addMonitor(mActivityStartMonitor)) to intercept subsequent activity launches.
2

2. startActivity

When an activity initiates navigation, the launch is intercepted and routed into a split container:

  • Layer 1: App / AndroidX The app calls standard startActivity(intent) without custom flags or layout checks.
  • Layer 2: OEM Extension Instrumentation.execStartActivity() triggers ActivityStartMonitor.onStartActivity() inside the app process before IPC:
    1. SplitController matches (who, intent) against registered rules.
    2. SplitPresenter evaluates current window bounds (e.g. width ≥ 600dp) and device fold posture.
    3. If satisfied, it retrieves/creates the target TaskFragmentContainer and injects ActivityOptions.KEY_LAUNCH_TASK_FRAGMENT_TOKEN.
  • Layer 3: Framework Client TaskFragmentOrganizer bundles container creation and bounds operations into an atomic TaskFragmentTransaction.
  • Layer 4: System Server (ATMS) ActivityStarter inspects options.getLaunchTaskFragmentToken(), verifies UID embedding security, and routes the new ActivityRecord directly into the designated TaskFragment. SurfaceFlinger smoothly composites both activities side-by-side.
3

3. finish

When an embedded activity finishes (user back press or finish() call):

  • Layer 1: App / AndroidX An activity invokes finish() or receives back navigation.
  • Layer 2: OEM Extension SplitController intercepts the container state change and evaluates the rule's FinishBehavior:
    • FINISH_NEVER: The adjacent activity remains open and expands to fill the parent Task.
    • FINISH_ALWAYS: Finishing one activity automatically finishes the associated activity in the other pane.
    • FINISH_ADJACENT: Associated activity is finished only when the two containers are actively displayed side-by-side.
  • Layer 3: Framework Client TaskFragmentOrganizer batches container removal and adjacent container bounds expansion into a TaskFragmentTransaction.
  • Layer 4: System Server (ATMS) TaskFragmentOrganizerController executes the transaction, destroying the finished container and expanding the remaining TaskFragment to full-screen with zero visual flickering.

4. Backward Compatibility by Design: Hierarchy Evolution & Rule-Based Model

Both the WindowManager hierarchy redesign and the rule-based embedding system share one foundational architectural goal: absolute backward compatibility. Existing multi-activity applications run without code rewrites, and the Android OS continues to manage tasks through established lifecycle contracts.

1. The Hierarchy Evolution: Task extends TaskFragment

In legacy Android, the OS contract assumed Task directly contained ActivityRecords and mapped 1:1 to a Recents entry. Rather than introducing a breaking new container type at the top level, Android 12L refactored the inheritance tree:

// Android 11 and earlier:
class Task extends WindowContainer<ActivityRecord> { ... }

// Android 12L and beyond:
class TaskFragment extends WindowContainer<WindowContainer> { ... }
class Task extends TaskFragment { ... }
// Android 12L+ Hierarchy:
RootWindowContainer
 └── DisplayContent
      └── TaskDisplayArea
           └── Task (Top-level TaskFragment, represents Recents tile)
                ├── TaskFragment 1 (Left / Primary Pane)
                │    └── ActivityRecord (e.g. ListActivity)
                └── TaskFragment 2 (Right / Secondary Pane)
                     └── ActivityRecord (e.g. DetailActivity)

Because Task extends TaskFragment, external system services (Launcher, Recents, ATMS) continue to treat a Task as a single unit. Internally, TaskFragment takes over managing individual activity stacks and multi-pane bounds. Existing single-pane apps simply run inside a default TaskFragment with zero awareness or behavioral change.

2. The Rule-Based Architecture

Similarly, the rule-based approach avoids breaking activity launch contracts. Instead of requiring new startActivity arguments or custom Intent flags, layout behavior is driven by centralized rules registered at startup:

// 1. Navigation call site remains standard:
startActivity(Intent(this, DetailActivity::class.java))

// 2. Rules registered once at startup:
val splitPairRule = SplitPairRule.Builder(
    filterSet = setOf(SplitPairFilter(
        ComponentName(this, ListActivity::class.java),
        ComponentName(this, DetailActivity::class.java),
        null
    ))
)
.setMinWidthDp(600)
.setDefaultSplitAttributes(
    SplitAttributes.Builder().setSplitType(SplitAttributes.SplitType.ratio(0.4f)).build()
)
.build()

RuleController.getInstance(context).setRules(setOf(splitPairRule))
Standard Call Sites Separation of Concerns

startActivity(intent) requires zero custom flags or window bounds checks. Navigation business logic is fully decoupled from presentation layout.

Dynamic Screen Adaptation Adaptive

Rules adapt dynamically at runtime. Folding, unfolding, or resizing seamlessly transitions between split and stacked layouts without restarting activities.

Zero UI Rewrites High Velocity

Multi-activity codebases gain large-screen and foldable support with XML or programmatic rules, avoiding multi-month Fragment or Compose migrations.

Coordinated Lifecycles Control

Declarative FinishBehavior (FINISH_ALWAYS, FINISH_ADJACENT, FINISH_NEVER) ensures predictable back-navigation across split containers.

5. Security & Trust Boundaries

Why can't malicious apps embed arbitrary banking or payment activities to intercept taps or steal user data? Android enforces strict trusted vs. untrusted embedding checks inside TaskFragment.java and ATMS ActivityStarter.

Trusted Embedding Same UID

Activities belonging to the same application package / UID are automatically trusted and can be embedded into adjacent TaskFragments freely without manifest opt-in.

Cross-App Embedding Cross-UID

When an app attempts to embed an activity from a different UID/package, the target activity must explicitly grant permission in its AndroidManifest.xml via one of two mechanisms:

1. Open Opt-In (Untrusted Embedding) Android 12L+

Allows any host app to embed this activity (e.g. public document viewers or sharing dialogs):

<activity
    android:name=".PublicShareActivity"
    android:allowUntrustedActivityEmbedding="true" />

Without this flag, the system server rejects the embedding transaction with a security exception, preventing tapjacking and overlay hijacking.

2. Certificate Verification (Restricted Partners) Android 14+ (API 34)

Restricts embedding exclusively to trusted partner apps verified by their SHA-256 signing certificate digest:

<activity
    android:name=".PartnerActivity"
    android:knownActivityEmbeddingCerts="@array/trusted_embedding_certs" />

ATMS validates the calling host's signing certificate against the referenced string array. Untrusted callers are blocked, enabling safe ecosystem splits without public exposure.

7. Appendix: The Architectural Secret — IoC via compileOnly & System Shared Library

How does an unbundled Jetpack library (androidx.window:window) shipped inside an application's APK communicate directly in-process with a device-specific OEM implementation (SplitController) inside frameworks/base, without runtime crashes, class duplication, or annual OS release coupling?

The secret lies in an elegant Inversion of Control (IoC) pattern orchestrated across three tiers using compileOnly dependencies, <uses-library>, and dynamic ClassLoader injection.

The 3-Tier Dependency & Loading Model Architecture

│ - Defines interface ActivityEmbeddingComponent                             │
│ - Defines entry point class WindowExtensionsProvider                        │
└───────────────────────┬─────────────────────────────┬───────────────────────┘
                        │ compileOnly                 │ static_libs

┌──────────────────────────────────────┐   ┌──────────────────────────────────┐
│ Tier 2: App Consumer                 │   │ Tier 3: Platform / OEM Provider  │

Runtime Injection Flow Step-by-Step

1

Process Launch & ClassLoader Mounting

When the app process forks from Zygote, ApplicationLoaders detects the <uses-library android:name="androidx.window.extensions" android:required="false" /> tag in the APK manifest and appends /system_ext/framework/androidx.window.extensions.jar to the app's PathClassLoader.

2

Entry Point Discovery

ExtensionEmbeddingBackend calls EmbeddingCompat.isEmbeddingAvailable(), which calls WindowExtensionsProvider.getWindowExtensions() on the device.

3

Component Instantiation in OEM Layer

WindowExtensionsImpl.getActivityEmbeddingComponent() instantiates the device's concrete mSplitController = new SplitController(...) and returns it typed as the ActivityEmbeddingComponent interface.

4

Defensive Reflection Guard

SafeActivityEmbeddingComponentProvider inspects the returned object at runtime, checking method signatures against the declared vendorApiLevel to prevent crashes on non-compliant OEM ROMs.

5

IoC Complete

EmbeddingCompat stores the validated ActivityEmbeddingComponent. High-level Jetpack rule changes now dispatch directly into the in-memory SplitController singleton!

Why compileOnly is the Key to Avoiding ClassLoader Collisions

In Java/Android, class identity is strictly determined by (Fully Qualified Name, ClassLoader). If androidx.window:window bundled WindowExtensions.class inside the APK's classes.dex, casting the object loaded from the system JAR would result in a fatal error: ClassCastException: WindowExtensions cannot be cast to WindowExtensions.

By declaring compileOnly in Gradle, the interface bytecode is completely stripped from the final APK. Exactly one single copy of WindowExtensions.class exists in memory at runtime—loaded from the system shared library!

Why Can androidx.window.extensions Be Customized While android.* Cannot?

The interface itself is declared in AndroidX (platform/frameworks/support) at WindowExtensions.java and imported into AOSP as a prebuilt static library (androidx.window.extensions_extensions-nodeps).

android.* (Strictly Immutable) Public Android SDK

Protected by the Android Compatibility Definition Document (CDD) and CTS. OEMs are strictly forbidden from modifying or extending signatures in android.*. Violating this fails CTS certification and prevents shipping Google Mobile Services (Google Play Store).

androidx.window.extensions.* (OEM Plugin) Vendor Extension Contract

Designed intentionally as a hardware-specific plugin interface. OEMs (Samsung, Pixel, OnePlus) have different physical hinges, folding angle thresholds, and multi-window UI rules. They are free to implement the internals of SplitController however their hardware requires, as long as it adheres to the contract and passes CtsWindowManagerJetpackTestCases.
