Android Activity Embedding Under the Hood

A comprehensive architectural exploration of how Android (12L+) and Jetpack WindowManager coordinate to run multiple activities side-by-side inside a single task without UI refactoring.

Platform: Android 12L (API 32) & Android 13+
Library: androidx.window:window:1.3+

1. Overview & Motivation

For over a decade, Android applications were designed around single-pane screens where each Activity occupied the full display. With the advent of foldables, tablets, and desktop modes, apps on large screens faced awkward letterboxing or stretched layouts.

Migrating multi-activity codebases into single-activity Fragment/Compose architectures requires immense time and risk. Activity Embedding solves this at the platform layer by allowing two or more activities from the same app (or explicitly permitted external apps) to be displayed simultaneously side-by-side or stacked.

Traditional Single-Activity Legacy

One activity fills the full task. Starting Activity B covers Activity A, sending A through onPause() / onStop().

Embedded Multi-Activity Modern

Task is divided into TaskFragments. Activity A and Activity B remain visible simultaneously and both are RESUMED (Multi-Resume).

2. The 4-Layer Architecture

Activity Embedding is not just a Jetpack library; it is a full-stack coordination involving AndroidX, an OEM dynamic bridge, Framework client IPC, and the WindowManager System Server.

Layer 1: Jetpack WindowManager (App Process) androidx.window.embedding

Public AndroidX developer API. Provides declarative XML rules, programmatic RuleController, and state observers. Translates high-level API into OEM extension interface calls.

▼ Dynamic Reflection / OEM Interface
Layer 2: WindowManager Extensions (OEM / AOSP) androidx.window.extensions.embedding

Shipped with the device OS or vendor image. Evaluates screen dimensions, folding state, aspect ratios, and builds atomic TaskFragmentTransaction operations.

▼ IPC via ITaskFragmentOrganizerController.aidl
Layer 3: Framework Core Client android.window

Client-side binder bridge. Defines atomic operation codes and wraps communication with WindowManager Service.

▼ Binder IPC to system_server (ATMS)

4. The Rule-Based Architecture & Advantages

Activity Embedding centralizes layout decisions into declarative or programmatic rules (e.g. SplitPairRule), completely isolating navigation logic from display geometry.

// 1. Navigation call site remains standard:
startActivity(Intent(this, DetailActivity::class.java))

// 2. Rules registered once at startup:
val splitPairRule = SplitPairRule.Builder(
    filterSet = setOf(SplitPairFilter(
        ComponentName(this, ListActivity::class.java),
        ComponentName(this, DetailActivity::class.java),
        null
    ))
)
.setMinWidthDp(600)
.setDefaultSplitAttributes(
    SplitAttributes.Builder().setSplitType(SplitAttributes.SplitType.ratio(0.4f)).build()
)
.build()

RuleController.getInstance(context).setRules(setOf(splitPairRule))
Standard Call Sites Separation of Concerns

startActivity(intent) requires zero custom flags or window bounds checks. Navigation business logic is fully decoupled from presentation layout.

Dynamic Screen Adaptation Adaptive

Rules adapt dynamically at runtime. Folding, unfolding, or resizing seamlessly transitions between split and stacked layouts without restarting activities.

Zero UI Rewrites High Velocity

Multi-activity codebases gain large-screen and foldable support with XML or programmatic rules, avoiding multi-month Fragment or Compose migrations.

Coordinated Lifecycles Control

Declarative FinishBehavior (FINISH_ALWAYS, FINISH_ADJACENT, FINISH_NEVER) ensures predictable back-navigation across split containers.

5. End-to-End Execution Sequence

The activity embedding lifecycle operates across three primary stages: setting the rules, intercepting activity launch, and coordinating finish.

1

1. Setting Rule with RuleController

At application startup (via Jetpack Startup or Application.onCreate), the app registers embedding rules:

RuleController.getInstance(context).setRules(setOf(splitPairRule));

AndroidX passes these rules via EmbeddingAdapter to the device's OEM SplitController.setEmbeddingRules(). SplitController installs an ActivityStartMonitor into the process's Instrumentation to monitor all subsequent activity launches.

2

2. startActivity

The app invokes standard startActivity(intent) without custom flags. The runtime sequence proceeds:

  1. Intercept: Instrumentation.ActivityMonitor intercepts onStartActivity(who, intent, options) in the app process before IPC.
  2. Rule Match & Metric Check: SplitController matches (who, intent) against registered rules and evaluates window metrics (e.g. width ≥ 600dp, fold posture).
  3. Token Injection: If matched, SplitController injects KEY_LAUNCH_TASK_FRAGMENT_TOKEN into ActivityOptions.
  4. ATMS Placement: ActivityTaskManagerService reads the token and routes the new ActivityRecord directly into the designated TaskFragment container, displaying both activities side-by-side.
3

3. finish

When an activity finishes (via user back press or finish() call):

  1. Evaluate FinishBehavior: The rule's configured finish policy determines dependent container behavior:
    • FINISH_NEVER: The adjacent activity remains open and expands to fill the parent Task.
    • FINISH_ALWAYS: Finishing one activity automatically finishes the associated activity in the other container.
    • FINISH_ADJACENT: Finishes the adjacent container only if both are currently displayed side-by-side.
  2. Atomic Cleanup: TaskFragmentOrganizer sends a TaskFragmentTransaction to ATMS to tear down the container and dynamically reconfigure remaining window bounds with zero visual flicker.

6. Security & Trust Boundaries

Why can't malicious apps embed arbitrary banking or payment activities to intercept taps? Android enforces strict trusted vs. untrusted embedding checks inside TaskFragment.java.

Trusted Embedding Same UID

Activities belonging to the same application package / UID are automatically trusted and can be embedded freely.

Untrusted Embedding Cross-App

Target activity must explicitly opt in via its AndroidManifest.xml:

<activity
    android:name=".ExternalActivity"
    android:allowUntrustedActivityEmbedding="true" />

Without this attribute, the system server rejects the embedding request, preventing tapjacking and overlay hijacking.

7. Interactive Dividers & Decor Surfaces

To let users drag the boundary between two split activities, the system does not redraw both activities on every frame. Instead, it utilizes a dedicated Decor Surface.

  • Operation: OP_TYPE_CREATE_OR_MOVE_TASK_FRAGMENT_DECOR_SURFACE creates a hardware SurfaceControl attached directly to the parent Task.
  • Draggability: DividerPresenter handles drag gestures and posts updated relative bounds to the organizer.
  • Performance: Resizing is performed at the compositor layer (SurfaceFlinger) before activities adapt their layout configurations.

9. Appendix: The Architectural Secret — IoC via compileOnly & System Shared Library

How does an unbundled Jetpack library (androidx.window:window) shipped inside an application's APK communicate directly in-process with a device-specific OEM implementation (SplitController) inside frameworks/base, without runtime crashes, class duplication, or annual OS release coupling?

The secret lies in an elegant Inversion of Control (IoC) pattern orchestrated across three tiers using compileOnly dependencies, <uses-library>, and dynamic ClassLoader injection.

The 3-Tier Dependency & Loading Model Architecture

Runtime Injection Flow Step-by-Step

1

Process Launch & ClassLoader Mounting

When the app process forks from Zygote, ApplicationLoaders detects the <uses-library android:name="androidx.window.extensions" android:required="false" /> tag in the APK manifest and appends /system_ext/framework/androidx.window.extensions.jar to the app's PathClassLoader.

2

Entry Point Discovery

ExtensionEmbeddingBackend calls EmbeddingCompat.isEmbeddingAvailable(), which calls WindowExtensionsProvider.getWindowExtensions() on the device.

3

Component Instantiation in OEM Layer

WindowExtensionsImpl.getActivityEmbeddingComponent() instantiates the device's concrete mSplitController = new SplitController(...) and returns it typed as the ActivityEmbeddingComponent interface.

4

Defensive Reflection Guard

SafeActivityEmbeddingComponentProvider inspects the returned object at runtime, checking method signatures against the declared vendorApiLevel to prevent crashes on non-compliant OEM ROMs.

5

IoC Complete

EmbeddingCompat stores the validated ActivityEmbeddingComponent. High-level Jetpack rule changes now dispatch directly into the in-memory SplitController singleton!

Why compileOnly is the Key to Avoiding ClassLoader Collisions

In Java/Android, class identity is strictly determined by (Fully Qualified Name, ClassLoader). If androidx.window:window bundled WindowExtensions.class inside the APK's classes.dex, casting the object loaded from the system JAR would result in a fatal error: ClassCastException: WindowExtensions cannot be cast to WindowExtensions.

By declaring compileOnly in Gradle, the interface bytecode is completely stripped from the final APK. Exactly one single copy of WindowExtensions.class exists in memory at runtime—loaded from the system shared library!

Why Can androidx.window.extensions Be Customized While android.* Cannot?

The interface itself is declared in AndroidX at androidx-window/window/extensions/extensions/src/main/java/androidx/window/extensions/WindowExtensions.java and imported into AOSP as a prebuilt static library (androidx.window.extensions_extensions-nodeps).

android.* (Strictly Immutable) Public Android SDK

Protected by the Android Compatibility Definition Document (CDD) and CTS. OEMs are strictly forbidden from modifying or extending signatures in android.*. Violating this fails CTS certification and prevents shipping Google Mobile Services (Google Play Store).

androidx.window.extensions.* (OEM Plugin) Vendor Extension Contract

Designed intentionally as a hardware-specific plugin interface. OEMs (Samsung, Pixel, OnePlus) have different physical hinges, folding angle thresholds, and multi-window UI rules. They are free to implement the internals of SplitController however their hardware requires, as long as it adheres to the contract and passes CtsWindowManagerJetpackTestCases.
