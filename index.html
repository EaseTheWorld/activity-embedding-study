Android Activity Embedding Under the Hood

A comprehensive architectural exploration of how Android (12L+) and Jetpack WindowManager coordinate to run multiple activities side-by-side inside a single task without UI refactoring.

Platform: Android 12L (API 32) & Android 13+
Library: androidx.window:window:1.3+
Core Hook: TaskFragmentOrganizer

1. Overview & Motivation

For over a decade, Android applications were designed around single-pane screens where each Activity occupied the full display. With the advent of foldables, tablets, and desktop modes, apps on large screens faced awkward letterboxing or stretched layouts.

Migrating multi-activity codebases into single-activity Fragment/Compose architectures requires immense time and risk. Activity Embedding solves this at the platform layer by allowing two or more activities from the same app (or explicitly permitted external apps) to be displayed simultaneously side-by-side or stacked.

Traditional Single-Activity Legacy

One activity fills the full task. Starting Activity B covers Activity A, sending A through onPause() / onStop().

Embedded Multi-Activity Modern

Task is divided into TaskFragments. Activity A and Activity B remain visible simultaneously and both are RESUMED (Multi-Resume).

2. The 4-Layer Architecture

Activity Embedding is not just a Jetpack library; it is a full-stack coordination involving AndroidX, an OEM dynamic bridge, Framework client IPC, and the WindowManager System Server.

Layer 1: Jetpack WindowManager (App Process) androidx.window.embedding

Public AndroidX developer API. Provides declarative XML rules, programmatic RuleController, and state observers. Translates high-level API into OEM extension interface calls.

3. Window Hierarchy Paradigm Shift

Key Source Insight: Task extends TaskFragment!

Prior to Android 12L, a Task directly managed ActivityRecords. In Android 12L+, the platform refactored the tree: class Task extends TaskFragment. A Task is now simply the top-level root TaskFragment that represents the user-visible entry in the Recents screen.

// Prior to 12L:
RootWindowContainer ➔ DisplayContent ➔ TaskDisplayArea ➔ Task ➔ ActivityRecord

// Android 12L+ (Activity Embedding Enabled):
RootWindowContainer
 └── DisplayContent
      └── TaskDisplayArea
           └── Task (Top-level TaskFragment, represents Recents tile)
                ├── TaskFragment 1 (Left / Primary Pane)
                │    └── ActivityRecord (e.g. ListActivity)
                └── TaskFragment 2 (Right / Secondary Pane)
                     └── ActivityRecord (e.g. DetailActivity)

4. The Mental Model: Why Rules, Not Flags

When Android developers first consider how to launch an activity into an adjacent split pane, an intuitive question arises: "Why can't we simply set an Intent flag?"

The Developer Intuition Existing Android Model

In standard Android development, the Intent object and its flags govern task and stack routing:

  • FLAG_ACTIVITY_NEW_TASK: Creates a new Task or brings an existing Task to the foreground.
  • FLAG_ACTIVITY_CLEAR_TOP: Clears intermediate activities above the destination on the stack.
  • FLAG_ACTIVITY_SINGLE_TOP: Delivers the Intent to onNewIntent() if already at the top of the stack.

Naturally, developers envision extending this pattern with an Intent flag for secondary stacks:

// What developers intuitively imagine:
val intent = Intent(this, DetailActivity::class.java).apply {
    flags = FLAG_ACTIVITY_SECONDARY_STACK // (Hypothetical flag!)
}
startActivity(intent)
Why Intent Flags Fail The Dynamic Reality

While intuitive, driving split layouts via Intent flags breaks down under the realities of modern multi-form-factor devices:

  • Dynamic Screen Posture: Foldable devices transition between folded (single compact pane, ~400dp width) and unfolded (wide dual-pane, ~840dp width) mid-session.
  • Static vs. Dynamic Decisions: An Intent flag is a static command issued at invocation time. But the decision to split must be dynamically evaluated at render time based on current window bounds.
  • Conflating Concerns: Hardcoding split flags at launch sites tangles navigation routing (what to open) with display presentation (how to render).
The Backward Compatibility Dilemma

Introducing new core flags to android.content.Intent requires updating the platform SDK and bumping the compile SDK. It offers no backwards compatibility for existing devices. Applications would be forced to guard every launch site with platform version checks and screen dimension checks before invoking startActivity().

The Architectural Solution: Centralized Embedding Rules

Android solved this architectural challenge by completely decoupling navigation from layout presentation through declarative and programmatic Rules registered at application startup:

1. Clean, Standard Navigation Unchanged Call Sites

Application navigation code remains completely standard and agnostic to screen layout. Activities invoke standard Android APIs:

// Normal startActivity call site:
val intent = Intent(this, DetailActivity::class.java)
startActivity(intent) // No custom flags or screen checks!

No device posture checks, no layout calculations, and no version branching at the point of invocation.

2. Centralized Rule Registration at Init RuleController

At application initialization (via Jetpack Startup or Application.onCreate), the app registers split rules:

val splitPairRule = SplitPairRule.Builder(
    filterSet = setOf(SplitPairFilter(
        ComponentName(this, ListActivity::class.java),
        ComponentName(this, DetailActivity::class.java),
        null
    ))
)
.setMinWidthDp(600)
.setDefaultSplitAttributes(
    SplitAttributes.Builder()
        .setSplitType(SplitAttributes.SplitType.ratio(0.4f))
        .build()
)
.build()

RuleController.getInstance(context).setRules(setOf(splitPairRule))
How Runtime Rules Bridge the Gap Dynamic Resolution

When startActivity() is called, the OEM SplitController intercepts the launch via Instrumentation.ActivityMonitor and performs runtime rule matching:

  • Folded / Compact State (< 600dp): The rule conditions are not met. SplitController allows the launch to proceed as a regular full-screen activity on top of the stack.
  • Unfolded / Expanded State (≥ 600dp): The rule matches! SplitController injects KEY_LAUNCH_TASK_FRAGMENT_TOKEN into ActivityOptions, directing WindowManager to position the new activity side-by-side in its own TaskFragment.
  • Fold / Unfold Mid-Session: When the user folds or unfolds the device while both activities are alive, the WindowManager hierarchy dynamically updates the layout between split and stacked without restarting or re-invoking the activities!

5. End-to-End Execution Sequence

What happens when an app invokes standard startActivity(intent) with split rules defined? How does an unbundled user-space rule intercept an OS-level activity launch without requiring custom launch flags in the calling code?

1

The Hook: Instrumentation.ActivityMonitor

During process initialization, the OEM SplitController hooks into the app process's Instrumentation instance:

// In SplitController.java:
Instrumentation instrumentation = activityThread.getInstrumentation();
mActivityStartMonitor = new ActivityStartMonitor();
instrumentation.addMonitor(mActivityStartMonitor);

Whenever any activity or context in the app calls startActivity(), Instrumentation.execStartActivity() invokes mActivityStartMonitor.onStartActivity(who, intent, options) before making any IPC call to the system server.

2

Rule Evaluation & Geometry Calculation (SplitPresenter)

Inside onStartActivity(), SplitController.resolveStartActivityIntent() matches (who, intent) against the rules set via Jetpack's RuleController. SplitPresenter evaluates device metrics (width/height vs minDimensions, folding posture) and calculates relative split bounds (e.g. 50/50 or 33/67).

3

The Token Injection: KEY_LAUNCH_TASK_FRAGMENT_TOKEN

SplitController prepares the target TaskFragmentContainer and injects its hidden token into the ActivityOptions bundle:

// In SplitController.java (ActivityStartMonitor):
options.putBinder(
    ActivityOptions.KEY_LAUNCH_TASK_FRAGMENT_TOKEN,
    launchedInTaskFragment.getTaskFragmentToken()
);

This allows the original startActivity() call to proceed normally, but now carries an internal instruction directed to WindowManager!

4

Atomic Transaction Assembly & Server Routing

JetpackTaskFragmentOrganizer dispatches a TaskFragmentTransaction to ITaskFragmentOrganizerController in system_server (ATMS). Simultaneously, ATMS's ActivityStarter inspects options.getLaunchTaskFragmentToken() and routes the new ActivityRecord directly into the designated TaskFragment container instead of creating a full-screen window.

5

Surface Synchronization & Shell Transitions

The WindowManager Shell and SurfaceFlinger execute an atomic transition animation. Both activities appear smoothly side-by-side without screen flickering or intermediate full-screen layouts.

6. Security & Trust Boundaries

Why can't malicious apps embed arbitrary banking or payment activities to intercept taps? Android enforces strict trusted vs. untrusted embedding checks inside TaskFragment.java.

Trusted Embedding Same UID

Activities belonging to the same application package / UID are automatically trusted and can be embedded freely.

Untrusted Embedding Cross-App

Target activity must explicitly opt in via its AndroidManifest.xml:

<activity
    android:name=".ExternalActivity"
    android:allowUntrustedActivityEmbedding="true" />

Without this attribute, the system server rejects the embedding request, preventing tapjacking and overlay hijacking.

7. Interactive Dividers & Decor Surfaces

To let users drag the boundary between two split activities, the system does not redraw both activities on every frame. Instead, it utilizes a dedicated Decor Surface.

  • Operation: OP_TYPE_CREATE_OR_MOVE_TASK_FRAGMENT_DECOR_SURFACE creates a hardware SurfaceControl attached directly to the parent Task.
  • Draggability: DividerPresenter handles drag gestures and posts updated relative bounds to the organizer.
  • Performance: Resizing is performed at the compositor layer (SurfaceFlinger) before activities adapt their layout configurations.

9. Appendix: The Architectural Secret — IoC via compileOnly & System Shared Library

How does an unbundled Jetpack library (androidx.window:window) shipped inside an application's APK communicate directly in-process with a device-specific OEM implementation (SplitController) inside frameworks/base, without runtime crashes, class duplication, or annual OS release coupling?

The secret lies in an elegant Inversion of Control (IoC) pattern orchestrated across three tiers using compileOnly dependencies, <uses-library>, and dynamic ClassLoader injection.

The 3-Tier Dependency & Loading Model Architecture

│ - Defines entry point class WindowExtensionsProvider                        │

Runtime Injection Flow Step-by-Step

1

Process Launch & ClassLoader Mounting

When the app process forks from Zygote, ApplicationLoaders detects the <uses-library android:name="androidx.window.extensions" android:required="false" /> tag in the APK manifest and appends /system_ext/framework/androidx.window.extensions.jar to the app's PathClassLoader.

2

Entry Point Discovery

ExtensionEmbeddingBackend calls EmbeddingCompat.isEmbeddingAvailable(), which calls WindowExtensionsProvider.getWindowExtensions() on the device.

3

Component Instantiation in OEM Layer

WindowExtensionsImpl.getActivityEmbeddingComponent() instantiates the device's concrete mSplitController = new SplitController(...) and returns it typed as the ActivityEmbeddingComponent interface.

4

Defensive Reflection Guard

SafeActivityEmbeddingComponentProvider inspects the returned object at runtime, checking method signatures against the declared vendorApiLevel to prevent crashes on non-compliant OEM ROMs.

5

IoC Complete

EmbeddingCompat stores the validated ActivityEmbeddingComponent. High-level Jetpack rule changes now dispatch directly into the in-memory SplitController singleton!

Why compileOnly is the Key to Avoiding ClassLoader Collisions

In Java/Android, class identity is strictly determined by (Fully Qualified Name, ClassLoader). If androidx.window:window bundled WindowExtensions.class inside the APK's classes.dex, casting the object loaded from the system JAR would result in a fatal error: ClassCastException: WindowExtensions cannot be cast to WindowExtensions.

By declaring compileOnly in Gradle, the interface bytecode is completely stripped from the final APK. Exactly one single copy of WindowExtensions.class exists in memory at runtime—loaded from the system shared library!

Why Can androidx.window.extensions Be Customized While android.* Cannot?

The interface itself is declared in AndroidX at androidx-window/window/extensions/extensions/src/main/java/androidx/window/extensions/WindowExtensions.java and imported into AOSP as a prebuilt static library (androidx.window.extensions_extensions-nodeps).

android.* (Strictly Immutable) Public Android SDK

Protected by the Android Compatibility Definition Document (CDD) and CTS. OEMs are strictly forbidden from modifying or extending signatures in android.*. Violating this fails CTS certification and prevents shipping Google Mobile Services (Google Play Store).

androidx.window.extensions.* (OEM Plugin) Vendor Extension Contract

Designed intentionally as a hardware-specific plugin interface. OEMs (Samsung, Pixel, OnePlus) have different physical hinges, folding angle thresholds, and multi-window UI rules. They are free to implement the internals of SplitController however their hardware requires, as long as it adheres to the contract and passes CtsWindowManagerJetpackTestCases.
