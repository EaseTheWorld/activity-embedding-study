Android Activity Embedding 내부 아키텍처 심층 분석

Android 12L(API 32) 및 Android 13+와 Jetpack WindowManager가 단일 태스크(Task) 내에서 여러 Activity를 분할 배치(Split)하여 호스팅하는 내부 동작 원리를 탐구합니다. 진정한 모듈화, 패키지 간 관심사 분리(SoC, Separation of Concerns), 그리고 완성도 높은 대화면 멀티페인 레이아웃 구현 메커니즘을 상세히 다룹니다.

플랫폼: Android 12L (API 32) & Android 13+ / AAOS
라이브러리: androidx.window:window:1.3+

1. 개요 및 도입 배경: 와이드 디스플레이 환경에서의 관심사 분리(SoC)

Android Automotive OS (AAOS) 중앙 센터페시아와 같은 고정형 대화면 와이드 디스플레이 환경에서는, 메인 차량 설정(Vehicle Settings) 앱이 런처 UI가 없는 음성 인식(Voice Recognition) 등 다양한 헤드리스(Headless) 백그라운드 서비스들의 통합 진입점 역할을 담당합니다. 기존의 모놀리식 단일 액티비티 구조는 관심사 분리(Separation of Concerns, SoC)를 심각하게 저해하는 안티패턴을 초래합니다:

2. 4계층 아키텍처 및 프로세스 경계

Activity Embedding은 단순한 단일 라이브러리가 아닙니다. 앱 프로세스 내부에서 동작하는 AndroidX 및 WindowManager Extensions와, 시스템 서버(system_server)의 WindowManager Core가 IPC를 통해 긴밀하게 협력하는 풀스택 아키텍처입니다. 개발자가 기존의 startActivity() 코드를 단 한 줄도 수정하지 않고 대화면 분할을 적용할 수 있도록, 선언적 규칙(Rule)이 4개 계층을 거치며 점진적으로 저수준 TaskFragment 트랜잭션으로 변환·실행됩니다.

Layer 1: Jetpack WindowManager
androidx.window.embedding 앱 프로세스

일반 앱 개발자가 직접 사용하는 공개 API 계층입니다. 앱 APK 내에 번들링되어 배포되며, 선언적 XML 규칙 및 프로그래밍 방식의 RuleController, 분할 상태 옵저버를 제공합니다.

규칙 선언 및 규격 변환 (Translate): 개발자가 선언한 분할 규칙(SplitPairRule 등)을 EmbeddingAdapter.translate()가 플랫폼 계약 규격(Java Predicate 및 Extensions 객체)으로 변환하여 Layer 2로 전달합니다.
SplitController.kt RuleController.kt SplitPairRule.kt ExtensionEmbeddingBackend.kt EmbeddingAdapter.kt
▼ 시스템 공유 라이브러리 동적 로딩 (<uses-library>) & 인터페이스 바인딩 (인프로세스)
Layer 2: WindowManager Extensions (시스템 공유 라이브러리)
androidx.window.extensions.embedding 앱 프로세스 (IoC)

규격 명세(AndroidX)와 플랫폼 구현체(AOSP/기기 제조사) 양쪽에 존재하며, 시스템 공유 라이브러리(<uses-library>) 동적 로딩과 IoC(제어의 역전)를 통해 앱 프로세스 메모리에 로드되는 동적 분할의 실질적인 런타임 두뇌입니다. (※ 리플렉션은 진입 시 메서드/클래스 존재 여부를 검증하는 방어적 가드일 뿐, 실제 바인딩은 공유 라이브러리 동적 마운트와 인터페이스 계약 다형성으로 이루어집니다.)

규칙 캐싱 및 startActivity 가로채기 (Intercept): 전달받은 규칙을 캐싱하고, 앱이 startActivity()를 호출하면 ActivityStartMonitor가 이를 가로채 화면 너비 등을 평가합니다. 분할 조건에 맞으면 타겟 TaskFragment를 생성하고 그 바인더 토큰(KEY_LAUNCH_TASK_FRAGMENT_TOKEN)을 Intent 옵션에 주입합니다.
SplitController.java SplitPresenter.java JetpackTaskFragmentOrganizer.java DividerPresenter.java
▼ 프레임워크 내부 인터페이스 호출 (인프로세스)
Layer 3: Framework Core Client (프레임워크 핵심 클라이언트)
android.window 앱 프로세스

Android 기본 플랫폼에 내장된 클라이언트 측 바인더 브리지입니다. 컨테이너 생성 및 바운드 설정 등의 작업을 원자적 TaskFragmentTransaction으로 묶어 시스템 서버로 전송할 수 있도록 캡슐화합니다.

원자적 트랜잭션 패키징 및 IPC 전송: Layer 2의 TaskFragment 조작 요청들을 TaskFragmentOrganizer가 원자적 WindowContainerTransaction (WCT)으로 묶어 system_server로 전송합니다.
TaskFragmentOrganizer.java TaskFragmentTransaction.java TaskFragmentOperation.java
⚡ 프로세스 간 경계 (Cross-Process Boundary: Binder IPC) ⚡
Layer 4: System Server & WindowManager Core (시스템 서버 코어)
com.android.server.wm system_server 프로세스

기기 전체의 창 관리를 총괄하는 ActivityTaskManagerService (ATMS) 시스템 서버 프로세스입니다. 컨테이너 경계 및 UID 보안 규칙을 강제하고, 액티비티 생명주기를 총괄하며, SurfaceControl 트랜잭션을 원자적으로 실행합니다.

트랜잭션 실행 및 액티비티 라우팅 (Routing): TaskFragmentOrganizerController가 트랜잭션을 실행해 윈도우 트리에 TaskFragment를 생성하고, ActivityStarter가 인텐트 옵션의 토큰을 읽어 새 액티비티를 해당 TaskFragment 안으로 정확히 라우팅하여 화면에 나란히 배치합니다.
TaskFragmentOrganizerController.java TaskFragment.java Task.java (TaskFragment 상속)
💡 핵심 멘탈 모델: Task와 Activity 사이에 도입된 TaskFragment 컨테이너 진화

Activity Embedding의 핵심을 가장 직관적으로 이해하는 방법은 "Task와 Activity 사이에 분할 화면을 담당하는 TaskFragment라는 창(Window) 단위 컨테이너가 새로 생겼다"고 파악하는 것입니다:

레거시 (Android 11 이전): Task (최근 앱 타일 1개) ──직접 포함──▶ Activity (화면 1개)
현재 (Android 12L 이후): Task (최근 앱 타일 1개) ──▶ TaskFragment (분할 창 단위) ──▶ Activity (화면 1개)

하나의 태스크 안에서 화면을 좌/우로 분할하고 각각의 윈도우 크기(Bounds)와 생명주기를 독립적으로 제어하기 위해 중간 컨테이너가 도입되었습니다. Layer 2(WindowManager Extensions)와 Layer 3(TaskFragmentOrganizer)가 앱 프로세스에서 이 TaskFragment들을 생성하고 바운드를 계산하며, Layer 4(ATMS)가 시스템 윈도우 트리에 이를 반영하여 화면에 나란히 합성(Composite)합니다.

3. 엔드투엔드 실행 흐름

Activity Embedding의 라이프사이클은 4가지 핵심 운영 흐름(Flow)에 걸쳐 동작합니다. 모든 작업은 앞서 살펴본 4개의 아키텍처 계층 간의 유기적 협력으로 완결됩니다:

1

1. RuleController를 통한 규칙(Rule) 등록

애플리케이션 시작 시점에 규칙들이 등록되고 프로세스에 바인딩됩니다:

RuleController.getInstance(context).setRules(setOf(splitPairRule));
  • Layer 1: App / AndroidX 앱이 고수준 규칙(예: SplitPairRule)을 생성하고 RuleController.setRules()를 호출합니다. EmbeddingAdapter가 이를 WindowManager Extensions 계약 인터페이스 규격으로 변환합니다.
  • Layer 2: WindowManager Extensions SplitController.setEmbeddingRules()가 규칙을 수신하고, 앱의 Instrumentation 인스턴스에 ActivityStartMonitor를 등록(instrumentation.addMonitor(mActivityStartMonitor))하여 이후 발생하는 액티비티 실행을 가로챌 수 있도록 준비합니다.
2

2. startActivity 호출 및 컨테이너 라우팅

액티비티가 화면 전환을 시작하면, 실행 요청이 가로채어져 분할 컨테이너로 라우팅됩니다:

  • Layer 1: App / AndroidX 앱은 커스텀 플래그나 별도의 레이아웃 검사 없이 표준 startActivity(intent)를 호출합니다.
  • Layer 2: WindowManager Extensions Instrumentation.execStartActivity()가 IPC 호출 이전에 앱 프로세스 내부의 ActivityStartMonitor.onStartActivity()를 트리거합니다:
    1. SplitController가 (who, intent) 쌍을 등록된 규칙들과 대조(Matching)합니다.
    2. SplitPresenter가 현재 윈도우 바운드(예: width ≥ 600dp) 및 디바이스 폴딩 상태를 평가합니다.
    3. 조건이 충족되면 대상 TaskFragmentContainer를 조회/생성하고 ActivityOptions.KEY_LAUNCH_TASK_FRAGMENT_TOKEN을 옵션에 주입합니다.
  • Layer 3: Framework Client TaskFragmentOrganizer가 컨테이너 생성 및 바운드 설정 작업을 원자적 TaskFragmentTransaction으로 패키징합니다.
  • Layer 4: System Server (ATMS) ActivityStarter가 options.getLaunchTaskFragmentToken()을 검사하고, UID 임베딩 보안을 검증한 후, 새 ActivityRecord를 지정된 TaskFragment로 직접 라우팅합니다. SurfaceFlinger가 두 액티비티를 깜빡임 없이 나란히 합성(Composite)합니다.
3

3. finish 처리 및 라이프사이클 조정

임베딩된 액티비티가 종료될 때 (사용자의 뒤로 가기 또는 finish() 호출):

  • Layer 1: App / AndroidX 액티비티가 finish()를 호출하거나 뒤로 가기 내비게이션 이벤트를 수신합니다.
  • Layer 2: WindowManager Extensions SplitController가 컨테이너 상태 변경을 감지하고 해당 규칙의 FinishBehavior를 평가합니다:
    • FINISH_NEVER: 인접 액티비티가 계속 열려 있으며, 부모 Task 전체 영역으로 자동 확장됩니다.
    • FINISH_ALWAYS: 한쪽 액티비티가 종료되면 다른 창의 연관된 액티비티도 함께 자동 종료됩니다.
    • FINISH_ADJACENT: 두 컨테이너가 나란히 분할 표시 중일 때만 연관 액티비티가 함께 종료됩니다.
  • Layer 3: Framework Client TaskFragmentOrganizer가 컨테이너 제거 및 인접 컨테이너 영역 확장 작업을 TaskFragmentTransaction으로 묶어 전달합니다.
  • Layer 4: System Server (ATMS) TaskFragmentOrganizerController가 트랜잭션을 실행하여, 종료된 컨테이너를 파괴하고 남은 TaskFragment를 시각적 깜빡임 없이 전체 화면으로 매끄럽게 확장합니다.
4

4. 동적 화면 너비 및 구성 변경 (Split ↔ Stacked)

화면 너비가 동적으로 변경될 때(기기 회전, 폴더블 접기/펼치기, 멀티윈도우 크기 조절), 레이아웃은 실시간으로 분할(Split)과 누적(Stacked) 상태 사이를 전환합니다:

  • Layer 4: System Server (ATMS) 부모 리프 Task의 바운드가 변경되었음을 감지합니다. ATMS는 SplitRule이나 분할 비율에 대해 전혀 알지 못하므로, 새 TaskFragmentParentInfo를 담은 TYPE_TASK_FRAGMENT_PARENT_INFO_CHANGED 트랜잭션을 디스패치합니다.
  • Layer 2: WindowManager Extensions (런타임 두뇌) JetpackTaskFragmentOrganizer가 트랜잭션을 수신하여 앱 프로세스 내부의 SplitController.onTaskFragmentParentInfoChanged()를 호출합니다:
    1. taskContainer.updateTaskFragmentParentInfo(parentInfo)가 캐시된 부모 태스크 치수를 갱신합니다.
    2. SplitPresenter.computeSplitAttributes()가 새 부모 바운드를 규칙의 minWidthDp 및 각 액티비티의 minDimensions와 비교 평가합니다.
    3. 레이아웃 결정:
      • 너비 < minWidthDp (화면이 좁아진 경우): EXPAND_CONTAINERS_ATTRIBUTES를 반환합니다. SplitPresenter.expandTaskFragment(wct, container)가 각 컨테이너를 전체화면 스택(Stacked) 구조로 전환합니다.
      • 너비 ≥ minWidthDp (화면이 충분히 넓은 경우): 비례적 상대 분할 바운드를 계산하고 SplitContainer를 업데이트합니다.
  • Layer 3: Framework Client 계산된 바운드 설정 및 확장 작업을 WindowContainerTransaction (WCT)에 담아 전달합니다.
  • Layer 4: System Server (ATMS) WindowOrganizerController.applyTransaction(wct)가 원자적 레이아웃 업데이트를 실행하여, 액티비티 재시작 없이 SurfaceControl 서피스들을 부드럽게 재배치하고 스케일링합니다.
💡 핵심 아키텍처: 동적 분할 변경은 어느 계층이 결정하는가?

화면 크기가 변경될 때 AndroidX(Layer 1)와 ATMS(Layer 4) 모두 레이아웃 분할 여부를 직접 계산하지 않습니다:

  • Layer 1 (AndroidX)은 앱 시작 시 규칙을 등록할 뿐이며, 런타임 지오메트리 계산을 전혀 수행하지 않습니다.
  • Layer 4 (ATMS)는 SplitRule이나 분할 비율(ratio)을 전혀 알지 못하며, 부모 바운드 변경 감지 시 TYPE_TASK_FRAGMENT_PARENT_INFO_CHANGED만 발행합니다.
  • Layer 2 (WindowManager Extensions: SplitController & SplitPresenter)가 앱 프로세스 내부에서 minWidthDp와 minDimensions를 비교 평가하여 분할(Split)할지 전체화면 누적(Stack, EXPAND_CONTAINERS_ATTRIBUTES)할지 결정하는 실질적인 동적 런타임 두뇌입니다.

4. 하위 호환성 설계: 계층 구조의 진화 및 규칙 기반 모델

WindowManager 계층 구조의 재설계와 규칙(Rule) 기반 임베딩 시스템은 한 가지 근본적인 아키텍처 목표를 공유합니다. 바로 완벽한 하위 호환성(Absolute Backward Compatibility)입니다. 기존의 멀티 액티비티 앱들은 코드 수정 없이 그대로 실행되며, Android OS는 기존의 표준 생명주기 계약에 따라 일관되게 태스크를 관리합니다.

1. 계층 구조의 진화: Task extends TaskFragment

레거시 Android에서 OS의 기본 계약은 Task가 ActivityRecord들을 직접 포함하며, 최근 앱(Recents) 타일과 1:1로 대응된다고 가정했습니다. 최상위 레벨에 기존 호환성을 깨뜨리는 새로운 컨테이너 타입을 도입하는 대신, Android 12L은 상속 계층 트리를 리팩터링했습니다:

// Android 11 및 이전:
class Task extends WindowContainer<ActivityRecord> { ... }

// Android 12L 및 이후:
class TaskFragment extends WindowContainer<WindowContainer> { ... }
class Task extends TaskFragment { ... }
// Android 12L+ 계층 구조:
RootWindowContainer
 └── DisplayContent
      └── TaskDisplayArea
           └── Task (최상위 TaskFragment, 최근 앱(Recents) 타일에 대응)
                ├── TaskFragment 1 (좌측 / 기본 창)
                │    └── ActivityRecord (예: ListActivity)
                └── TaskFragment 2 (우측 / 보조 창)
                     └── ActivityRecord (예: DetailActivity)

Task가 TaskFragment를 상속하기 때문에, 외부 시스템 서비스들(Launcher, Recents, ATMS)은 여전히 Task를 단일 단위로 취급합니다. 내부적으로는 TaskFragment가 개별 액티비티 스택과 멀티페인 바운드를 독립적으로 관리합니다. 기존의 단일 창 앱들은 기본 TaskFragment 안에서 아무런 동작 변경이나 호환성 문제 없이 그대로 실행됩니다.

💡 화면 분할 시 어떤 액티비티가 최상위(Top)인가? Multi-Resume & Z-Order

Primary와 Secondary 액티비티가 모두 화면에 표시되어 RESUMED 상태(Multi-Resume)라 하더라도, WindowManager 내부 컨테이너 트리에서는 Secondary Activity가 항상 선형 Z-order 상위(Top)로 관리됩니다. 따라서 singleTop 플래그 호출 등의 동작 시 Secondary가 최상위로 평가됩니다.

👉 ATMS 자식 인덱스 탐색 알고리즘, singleTop/clearTop 상세 동작, AOSP 테스트 코드 검증은 부록 B: Top Activity 판정과 Z-Order 심층 분석을 참조하세요.

2. 규칙 기반(Rule-Based) 아키텍처

마찬가지로 규칙 기반 접근 방식은 기존 액티비티 실행 계약을 해치지 않습니다. startActivity에 새로운 인자를 요구하거나 커스텀 Intent 플래그를 추가하는 대신, 앱 시작 시 등록된 중앙화된 규칙에 따라 레이아웃 동작이 제어됩니다:

// 1. 화면 전환 호출부는 표준 코드 그대로 유지:
startActivity(Intent(this, DetailActivity::class.java))

// 2. 앱 시작 시점에 한 번만 등록되는 규칙:
val splitPairRule = SplitPairRule.Builder(
    filterSet = setOf(SplitPairFilter(
        ComponentName(this, ListActivity::class.java),
        ComponentName(this, DetailActivity::class.java),
        null
    ))
)
.setMinWidthDp(600)
.setDefaultSplitAttributes(
    SplitAttributes.Builder().setSplitType(SplitAttributes.SplitType.ratio(0.4f)).build()
)
.build()

RuleController.getInstance(context).setRules(setOf(splitPairRule))
표준 호출부 유지 (Standard Call Sites) 관심사 분리

startActivity(intent) 호출 시 커스텀 플래그나 윈도우 바운드 검사가 필요 없습니다. 화면 이동 비즈니스 로직과 화면 배치 레이아웃이 완전히 분리됩니다.

동적 화면 적응 (Dynamic Screen Adaptation) 반응형

규칙은 런타임에 동적으로 적용됩니다. 폴더블 기기를 접거나 펼칠 때, 혹은 창 크기를 조절할 때 액티비티 재시작 없이 분할(Split)과 누적(Stacked) 레이아웃 사이를 매끄럽게 전환합니다.

UI 전면 재작성 불필요 (Zero UI Rewrites) 높은 생산성

기존 멀티 액티비티 코드베이스에서 XML 또는 코드로 몇 줄의 규칙만 추가하면 대화면 및 폴더블을 즉시 지원할 수 있으므로, 수개월이 소요되는 Fragment나 Compose 전면 마이그레이션을 피할 수 있습니다.

조율된 생명주기 (Coordinated Lifecycles) 정밀한 제어

선언적 FinishBehavior (FINISH_ALWAYS, FINISH_ADJACENT, FINISH_NEVER) 설정을 통해 분할 컨테이너 간의 예측 가능한 뒤로 가기 내비게이션을 보장합니다.

5. 보안 및 신뢰 경계

악의적인 앱이 임의의 금융 또는 결제 액티비티를 임베딩하여 사용자 터치를 가로채거나(Tapjacking) 화면을 탈취하는 것을 어떻게 방지할까요? Android는 TaskFragment.java와 ATMS ActivityStarter 내부에서 엄격한 신뢰(Trusted) 대 비신뢰(Untrusted) 임베딩 검사를 수행합니다.

1. 동일 앱 임베딩 (Same UID / Trusted Embedding) 동일 UID · 자동 신뢰

동일한 애플리케이션 패키지 및 UID에 속한 액티비티들은 자동으로 신뢰되며, 매니페스트(AndroidManifest.xml)에 별도의 허용 설정을 하지 않아도 인접한 TaskFragment에 자유롭게 임베딩될 수 있습니다.

2. 교차 앱 임베딩 (Cross-UID / Cross-App Embedding) 교차 UID · 명시적 허용 필수

서로 다른 UID/패키지의 액티비티를 임베딩하려는 경우, 대상 액티비티(임베딩되는 앱)가 AndroidManifest.xml을 통해 임베딩 권한을 명시적으로 부여해야 합니다. 시스템은 보안 요구수준에 따라 2가지 하위 허용 방식을 제공합니다:

방식 A. 공개 허용 (비신뢰 임베딩) Android 12L+

어떤 호스트 앱이라도 이 액티비티를 임베딩할 수 있도록 전면 허용합니다 (예: 공용 문서 뷰어, 범용 공유 대화상자):

<activity
    android:name=".PublicShareActivity"
    android:allowUntrustedActivityEmbedding="true" />

⚠️ 이 플래그가 없으면 시스템 서버가 보안 예외(SecurityException)를 발생시키며 트랜잭션을 즉시 차단합니다. 누구나 임베딩할 수 있으므로 민감한 UI에는 주의가 필요합니다.

방식 B. 인증서 검증 (제한된 파트너) Android 13+ (API 33)

지정된 SHA-256 서명 인증서 다이제스트가 일치하는 신뢰할 수 있는 특정 파트너 앱에게만 임베딩을 제한적으로 허용합니다:

<activity
    android:name=".PartnerActivity"
    android:knownActivityEmbeddingCerts="@array/trusted_embedding_certs" />

✅ ATMS가 호스트 앱의 서명 인증서를 대조하여 검증합니다. 인가되지 않은 앱의 임베딩은 시스템 레벨에서 완전 차단되므로 안전한 파트너 간 화면 분할이 가능합니다 (Android 14부터 최대 50개 제한 검증 추가).

부록 A. 아키텍처의 비밀 — compileOnly 및 시스템 공유 라이브러리를 통한 IoC

애플리케이션 APK 내부에 번들링된 비번들(Unbundled) Jetpack 라이브러리(androidx.window:window)가 런타임 크래시나 클래스 중복, 연간 OS 판올림 종속성 없이 어떻게 시스템 파티션에 위치한 기기 플랫폼 구현체(SplitController)와 동일 프로세스(In-process) 내에서 직접 통신할 수 있을까요?

그 비밀은 compileOnly 의존성, <uses-library>, 그리고 동적 ClassLoader 마운트를 유기적으로 결합한 우아한 제어의 역전(Inversion of Control, IoC) 아키텍처 패턴에 있습니다.

3계층 의존성 및 로딩 모델 (3-Tier Dependency & Loading Model) 아키텍처 
┌─────────────────────────────────────────────────────────────────────────────┐
│ Tier 1: 규격 명세 계약 (androidx.window:window-extensions)                  │
│ - WindowExtensions 인터페이스 정의                                          │
│ - ActivityEmbeddingComponent 인터페이스 정의                                │
│ - 진입점 클래스 WindowExtensionsProvider 정의                                │
└───────────────────────┬─────────────────────────────┬───────────────────────┘
                        │ compileOnly                 │ static_libs
                        ▼                             ▼
┌──────────────────────────────────────┐   ┌──────────────────────────────────┐
│ Tier 2: 앱 소비자 (App Consumer)      │   │ Tier 3: 플랫폼 / 기기 구현체      │
│ (APK 내부의 androidx.window:window)  │   │ (/system_ext/framework/...)      │
├──────────────────────────────────────┤   ├──────────────────────────────────┤
│ - compileOnly(window-extensions)     │   │ - static_libs: [window-extensions]│
│ - AndroidManifest.xml:               │   │ - WindowExtensionsImpl           │
│   <uses-library                      │   │   implements WindowExtensions    │
│     name="androidx.window.extensions"│   │ - SplitController                │
│     required="false" />              │   │   implements                     │
│ - ExtensionEmbeddingBackend.kt       │   │   ActivityEmbeddingComponent     │
│ - SafeActivityEmbeddingComponent-    │   │                                  │
│   Provider.kt                        │   │                                  │
└──────────────────────────────────────┘   └──────────────────────────────────┘

단계별 런타임 주입 흐름 (Runtime Injection Flow Step-by-Step)

1

프로세스 기동 및 ClassLoader 마운팅

앱 프로세스가 Zygote로부터 포크(fork)될 때, ApplicationLoaders가 APK 매니페스트 내의 <uses-library android:name="androidx.window.extensions" android:required="false" /> 태그를 감지하고 기기의 /system_ext/framework/androidx.window.extensions.jar를 앱의 PathClassLoader에 추가 마운트합니다.

2

진입점 탐색 (Entry Point Discovery)

ExtensionEmbeddingBackend가 EmbeddingCompat.isEmbeddingAvailable()을 호출하고, 이는 기기 플랫폼 상의 WindowExtensionsProvider.getWindowExtensions()를 호출합니다.

3

WindowManager Extensions 컴포넌트 인스턴스화

WindowExtensionsImpl.getActivityEmbeddingComponent()가 기기 고유의 구체 클래스 인스턴스인 mSplitController = new SplitController(...)를 생성하고 이를 ActivityEmbeddingComponent 인터페이스 타입으로 반환합니다.

4

방어적 리플렉션 가드: 메서드 검증 (Defensive Reflection Guard)

리플렉션의 실질적인 역할은 바인딩 메커니즘 자체가 아니라 안전성 검증 가드(Guard)입니다. SafeActivityEmbeddingComponentProvider 및 ReflectionUtils가 런타임에 리플렉션으로 객체를 조사하여 선언된 vendorApiLevel과 필수 메서드 시그니처가 실제로 온전히 존재하는지 사전 검증(Method Verification)함으로써, 비표준 기기 ROM 환경에서 NoSuchMethodError나 ClassNotFoundException으로 앱이 강제 종료되는 것을 방지합니다. 검증이 통과하면 이후 모든 호출은 리플렉션 오버헤드 없이 순수 Java 인터페이스 다형성으로 고속 디스패치됩니다.

5

IoC 주입 완료 (IoC Complete)

EmbeddingCompat이 검증된 ActivityEmbeddingComponent를 저장합니다. 이제 고수준 Jetpack 규칙 변경 호출이 메모리 상의 SplitController 싱글톤으로 직접 디스패치됩니다!

compileOnly가 ClassLoader 충돌을 방지하는 핵심 열쇠인 이유

Java/Android 런타임에서 클래스의 동일성은 (클래스 전체 경로, ClassLoader)의 조합으로 엄격히 결정됩니다. 만약 androidx.window:window가 APK 내부의 classes.dex에 WindowExtensions.class를 직접 포함해 배포한다면, 시스템 JAR에서 로드된 객체로 형변환(Casting)할 때 치명적인 런타임 오류(ClassCastException: WindowExtensions cannot be cast to WindowExtensions)가 발생합니다.

Gradle에서 compileOnly로 선언함으로써, 해당 인터페이스의 바이트코드는 최종 APK 파일에서 완전히 제거됩니다. 따라서 런타임 메모리에는 시스템 공유 라이브러리에서 로드된 단 하나의 WindowExtensions.class만 존재하게 됩니다!

android.*는 수정할 수 없는데 왜 androidx.window.extensions는 커스터마이징이 가능할까?

인터페이스 자체는 AndroidX(platform/frameworks/support)의 WindowExtensions.java에 선언되어 있으며, 사전 빌드된 정적 라이브러리(androidx.window.extensions_extensions-nodeps) 형태로 AOSP에 임포트됩니다.

android.* (엄격한 불변성) 공개 Android SDK

Android 호환성 정의 문서(CDD)와 CTS(호환성 테스트 슈트)에 의해 보호됩니다. 기기 제조사는 android.* 패키지 내부의 메서드 시그니처를 임의로 수정하거나 확장하는 것이 엄격히 금지됩니다. 이를 위반하면 CTS 인증에 실패하여 GMS(Google Play 스토어 등) 탑재가 불가능해집니다.

androidx.window.extensions.* (WindowManager Extensions) 벤더 확장 계약

처음부터 하드웨어 특화 플러그인 인터페이스로 의도되어 설계되었습니다. 제조사(삼성, 픽셀, 원플러스 등)마다 물리적 힌지 구조, 폴딩 각도 임계값, 멀티윈도우 UI 정책이 모두 다릅니다. 따라서 제조사는 인터페이스 규격을 준수하고 CtsWindowManagerJetpackTestCases를 통과하기만 하면, 자사 하드웨어 요구에 맞춰 SplitController의 내부 구현을 자유롭게 최적화할 수 있습니다.

부록 B. Multi-Resume 환경에서의 Top Activity 판정과 Z-Order 심층 분석

Android 10부터 도입된 멀티-리쥼(Multi-Resume) 환경에서는 분할된 두 화면(Primary와 Secondary)의 액티비티가 동시에 화면에 보이고 모두 RESUMED 생명주기 상태를 유지합니다. 그렇다면 시스템 레벨(ATMS)에서 "현재 태스크의 최상위 액티비티(Top Activity)는 누구인가?"를 판단할 때 어떤 원칙이 적용될까요? AOSP 소스 레벨에서 컨테이너 순서와 Intent 플래그 동작 원리를 상세히 분석합니다.

태스크 내 TaskFragment 계층 및 Z-Order 인덱스 구조 AOSP 구조 
Task (최상위 WindowContainer)
 ├── mChildren[0]: TaskFragment 1 (Primary / 기본 창, ListActivity)
 └── mChildren[1]: TaskFragment 2 (Secondary / 보조 창, DetailActivity) ◀── [Top Activity!]

1. ATMS 내부 컨테이너 배치 순서: pairedPosition + 1

AOSP의 WindowOrganizerController.java:2583에 따르면, 보조 컨테이너(TaskFragment 2)가 생성되어 기본 컨테이너(TaskFragment 1)와 쌍(Pair)을 이룰 때 시스템 서버는 다음과 같이 자식을 삽입합니다:

// frameworks/base/services/core/java/com/android/server/wm/WindowOrganizerController.java
final int position = mTask.mChildren.indexOf(primaryTaskFragment) + 1;
mTask.addChild(secondaryTaskFragment, position);

즉, Secondary TaskFragment는 항상 Primary TaskFragment의 바로 위 인덱스(상위 위치)에 위치하게 됩니다.

2. 최상위 액티비티 탐색 알고리즘: 역순 탐색 (Top-Down Search)

ActivityTaskManagerService(ATMS)가 태스크의 최상위 실행 액티비티를 조회할 때(Task.topRunningActivity()), WindowContainer.java:2044에 정의된 공통 컨테이너 탐색 로직을 실행합니다:

// frameworks/base/services/core/java/com/android/server/wm/WindowContainer.java
for (int i = mChildren.size() - 1; i >= 0; --i) {
    final ActivityRecord r = mChildren.get(i).topRunningActivity();
    if (r != null) {
        return r;
    }
}

리스트의 가장 높은 인덱스(역순)부터 탐색하므로, 나란히 분할 표시되어 양쪽이 모두 포커스를 받을 수 있는 상태라도 시스템은 언제나 SecondaryActivity를 태스크의 "Top Activity"로 평가합니다.

3. Intent 시작 플래그(singleTop / clearTop)에 미치는 영향

singleTop 단독 사용 시 onNewIntent 미호출

singleTop 플래그는 개별 TaskFragment가 아닌 태스크 전체의 최상위(Top)를 기준으로 평가됩니다. 현재 최상위 액티비티는 Secondary이므로, PrimaryActivity를 singleTop으로 재실행해도 Top으로 인정받지 못해 onNewIntent()가 호출되지 않으며, 새 액티비티 인스턴스가 생성됩니다.

FLAG_ACTIVITY_CLEAR_TOP 사용 시 정상 onNewIntent 호출

CLEAR_TOP 플래그는 대상 액티비티보다 상위 Z-order에 존재하는 모든 액티비티를 정리(스택에서 제거)합니다. 따라서 SecondaryActivity가 파괴(finish)된 후, 최상위가 된 PrimaryActivity로 정상적인 onNewIntent()가 전달됩니다.

4. AOSP 플랫폼 단위 테스트 검증

Google WindowManager 팀은 TaskContainerTest.java:186-188 단위 테스트를 통해 보조 액티비티가 태스크 컨테이너의 최상위 비종료 액티비티임을 명시적으로 단언(assert)하여 검증하고 있습니다:

// WindowManager Jetpack 테스트 코드 검증 (TaskContainerTest.java:186-188)
assertEquals(activity1, taskContainer.getTopNonFinishingActivity(true));
// activity1(보조 액티비티)이 항상 getTopNonFinishingActivity의 결과로 반환됨을 검증
